# Hosted connectors

How each connector signs people in, and the OAuth app or key it needs.

The tools service reads `https://app.signalbox.run/catalog/index.json`. A separate read-only Worker serves official catalog entries and contributed app sources. Entries carry no notices: every app lists with its one-sentence description. The contributed Slack user-token method is carried as a pinned package snapshot until its upstream release. The Zendesk source is served by the Catalog Worker independently of optional hosted credentials. New app sources stay with the catalog while community publication awaits an approved publisher scope and checks against the chosen public host. Relative icons resolve to the official publisher. The feed is outside the tools API Worker bundle; the existing 5.45 MB upload budget stays unchanged.

A connection requests only its selected app's scopes. The all-in-one Google app requests this broader scope union; see [its scope and API readiness check](google-connector-readiness.md). The official Google Admin app uses the same hosted Google client with a separate set of Admin SDK scopes. See [the Google Admin registration packet](google-admin-registration.md) for the exact scope list and API setup. Full Gmail and Drive access is intentional. The identity-only sign-in client stays independent of connector grants, consent and rotation. Two clients in one project would still share the project's user cap.

Create a separate GitHub OAuth App named Signalbox with homepage `https://app.signalbox.run` and callback `https://app.signalbox.run/api/oauth/callback`. The official REST app requests `repo`, `read:org`, `workflow`, `gist`, `notifications`, `read:user` and `user:email`. The host's optional `github-oauth` client matches this app; its older GitHub App client remains separate. No app review is required. Organization approval and SAML sign-in can still limit repository access.

Google and GitHub connector credentials are optional and use the four `EXECUTOR_OAUTH_*` secrets in [GitHub Actions secrets](self-hosting.md#github-actions-secrets). GitHub Actions supplies them and Alchemy writes their runtime copies. No person enters a client secret to connect their account. Missing or incomplete pairs are omitted, with one deployment warning per unavailable connector. Sign-in, pools and computer setup deploy independently.

GitLab uses the [carried site-aware app](../src/catalog/gitlab.json). GitLab.com keeps the hosted one-click OAuth client when its optional credentials are configured. Its `api` scope includes `read_user` and grants write access; mutating tools still require approval.

For each self-managed instance, create a separate confidential OAuth application on that instance. Enable authorization-code and refresh-token access, set callback `https://app.signalbox.run/api/oauth/callback`, and request `api` and `read_user`. In Basalt, add a separate GitLab account for each instance, enter its exact HTTPS origin, then enter that instance's OAuth client ID and secret. The shared GitLab.com client is never sent to a self-managed origin. A reconnect keeps the saved origin; add another account to connect a different instance.

You can connect with a personal, project, or group access token instead. Use `api` for full access or `read_api` for read-only access. The token and OAuth grant are sent only to the saved origin. Existing GitLab.com accounts keep their account IDs and reconnect to `https://gitlab.com`; the first reconnect saves that origin, so no data migration is needed.

Private instances need an exact origin entry in `EXECUTOR_URL_ALLOW_HTTP_ORIGINS` on the deployment, plus network access from the tools service. Include the scheme and port in the JSON array. The exception covers only that origin. Other hosts, ports, and redirects remain refused.

Miro uses the retained operations from its [pinned official REST API v2 package](../src/catalog/miro.json). The app and optional hosted client request the eleven scopes selected in the Developer Hub: `boards:read`, `boards:write`, `identity:read`, `identity:write`, `microphone:listen`, `screen:record`, `team:read`, `team:write`, `webcam:record`, `auditlogs:read` and `sessions:delete`. Miro documents the microphone, screen and webcam scopes for Web SDK capture; this REST app does not use the Web SDK. The router exposes board, organization, team, group, export, audit and session operations, excluding nine SCIM paths, a malformed group-delete path and the deprecated token-in-URL revoke operation. The selected set does not include Miro's separately documented `organizations:read`, `organizations:teams:read` or `organizations:teams:write` scopes, so organization operations may be refused by Miro until the app can request the required grants. Miro still enforces account roles and plan limits; audit and session administration require Enterprise and Company Admin access. OAuth is the first method; a custom OAuth client or access token remains available under Advanced. Every mutation asks for approval. The saved grant is not evidence of native authorization or live API acceptance.

To verify the complete Miro tool list, save the API document at the `specCommit` recorded in [its provenance](../src/catalog/miro.provenance.json), then run `bun scripts/connectors-tests/miro-tools.mjs <saved-spec.json>` after preparing and building the pinned framework. The check verifies both SHA-256 digests, compares the app's OAuth declaration with the host definition, and compiles every retained operation through the public framework API. It makes no provider requests.

Supply `EXECUTOR_OAUTH_GITLAB_CLIENT_ID`, `EXECUTOR_OAUTH_GITLAB_CLIENT_SECRET`, `EXECUTOR_OAUTH_MIRO_CLIENT_ID` and `EXECUTOR_OAUTH_MIRO_CLIENT_SECRET` through GitHub Actions. The GitLab pair is used only for `https://gitlab.com`; it is not used for self-managed instances. These pairs use the same optional-client behavior as Google and GitHub. The tools API receives only the hosted-client metadata and secret bindings; no connector package or API schema is added to its bundle.

Notion, Todoist and Trello keep their official catalog sources and existing custom-client and token methods. Optional hosted clients use the paired `EXECUTOR_OAUTH_NOTION_*`, `EXECUTOR_OAUTH_TODOIST_*` and `EXECUTOR_OAUTH_TRELLO_*` Actions secrets. Each person authorizes a separate account; a shared OAuth registration does not share their grants. Missing or incomplete pairs are omitted during deployment, and previews receive none of these credentials. Registration, vendor review and live acceptance remain separate from this wiring.

Register each application as Signalbox, with callback `https://app.signalbox.run/api/oauth/callback`:

- **Notion:** the public OAuth app is registered with content and comments read/write, plus user information including email. It remains unpublished and has no Marketplace submission. OAuth has no scope list. Authorization uses `https://api.notion.com/v1/oauth/authorize` with `owner=user`; token and refresh requests use `https://api.notion.com/v1/oauth/token`, HTTP Basic client authentication and JSON. - **Todoist:** create an OAuth application with `data:read_write`, `data:delete` and `project:delete`. - **Trello:** create an Atlassian confidential OAuth 2.0 application for Trello. Configure `read:board:trello`, `write:board:trello`, `write:board:membership:trello`, `read:organization:trello`, `write:organization:trello`, `write:organization:membership:trello`, `read:member:trello`, `write:member:trello`, `read:enterprise:trello` and `write:enterprise:trello`. The authorization request also asks for `offline_access`; it is not a selectable scope in the client settings. The current catalog uses `https://auth.atlassian.com/authorize` with `prompt=consent` and JSON exchanges at `https://auth.atlassian.com/oauth/token`. The vendor's confidential-client documentation contains conflicting token paths; this implementation follows its code example and the catalog. Live bearer-token acceptance at `api.trello.com` remains unverified. The existing API key and token method remains available.

The real self-host proof checks the configured callback on shared and BYO starts against the canonical vendor endpoints. A second scenario translates only issuer URLs and credential placement to the existing synthetic OAuth fixture, retains each vendor's scopes, token encoding and client authentication, and completes grants for two users. It checks distinct personal accounts and peer refusal. These scenarios do not establish live vendor consent or API acceptance.

Miro reuses its existing optional hosted client and the eleven scopes above. The hosted pair remains optional and incomplete pairs stay omitted.

Create an Atlassian OAuth 2.0 (3LO) app in the developer console named after `brand.oauthAppName` (Signalbox), with callback `https://app.signalbox.run/api/oauth/callback`. Keep sharing off until the reporting implementation is merged and released and a real 3LO grant successfully calls the reporting endpoint. Add `read:me` for identity refresh, `read:jira-work` for Jira and `read:confluence-content.all` and `search:confluence` for Confluence. The app also requests `offline_access` for rotating refresh tokens. Authorization sends `audience=api.atlassian.com` and `prompt=consent`, and token exchanges use JSON. Atlassian's unreviewed-app warning is accepted for v1. Each person connects their own account; their site's permissions and app access policies still apply. Add the client ID and secret to the two `EXECUTOR_OAUTH_ATLASSIAN_*` [GitHub Actions secrets](self-hosting.md#github-actions-secrets). Both may be absent during deployment.

The combined Atlassian app uses private package name `atlassian`. Its public source baseline, fork revision, file hashes and MIT license are under `src/catalog/atlassian/`. The replayable source patch pins the exact Basalt SDK and adds four OpenAPI routers: Jira Platform, Jira Service Management, Confluence v1 and Confluence v2. They retain 1,038 operations and require approval on every mutation. The five curated reads remain available without approval. The package requests 73 scopes, preferring classic scopes where supported. Additional granular scopes still need shared-client registration and live consent verification. Connect/Forge-owned routes, operations without OAuth support and beta scopes are excluded with reasons in the package's `api-coverage.json`. The adapter applies operation-specific headers and disambiguates Confluence v2's documented flat and nested page bodies. Community publication awaits an approved publisher scope and checks against the chosen public host; [upstream source issue #2370](https://github.com/UsefulSoftwareCo/executor/issues/2370) stays open until publication. Its hosted-client metadata remains a separate Basalt-only tools-service overlay. The provider-specific [PR #2367](https://github.com/UsefulSoftwareCo/executor/pull/2367) is closed unmerged, with the generic operator-configuration proposal tracked in [issue #2382](https://github.com/UsefulSoftwareCo/executor/issues/2382).

The hosted Atlassian client opts into the generic [scheduled personal-data reporter](https://github.com/UsefulSoftwareCo/executor/pull/2467). It refreshes identity at `https://api.atlassian.com/me`, reads `account_id`, and reports to `https://api.atlassian.com/app/report-accounts/` through the same owner's authorized 3LO grant. Existing grants may need reconnecting to consent to `read:me`; the app-wide client credentials stay unchanged. No Forge-only reporting scope is requested. The existing optional client pair is already forwarded to the Cloud host, so reporting introduces no additional deployment secret.

Self-host and local poll every 15 minutes; Cloud polls at minutes 7, 22, 37 and 52. Stored subject schedules keep reports at least seven days apart by default and honor `Cycle-Period` and `Retry-After`. Requests contain at most 90 distinct account IDs per owner and registration. An `updated` result refreshes the subject's identity. A `closed` result erases saved user credentials and identity copies, cancels pending reconnects and shows a generic notice. App client configuration and other registrations remain usable. The additive storage migration keeps existing site selections and account data. Synthetic tests cover these paths and reporting telemetry privacy; live Atlassian eligibility, reporting permission and consent remain unverified.

Installed Claude Code and Codex use isolated homes, the production config installer and a local model fixture. The isolated Codex process explicitly approves only Signalbox's `call` tool for these read requests. Private diagnostics remain under `.generated/atlassian-proof`. This proves local integration and account isolation; production consent, an actual shared pool and live site access remain separate acceptance checks.

Slack uses the official Web API app with an additional personal user-token OAuth method. Its authorization request sends `user_scope` only and reads `authed_user.access_token`. Create a Slack app named Signalbox from [its registration manifest](../src/catalog/slack.manifest.json), enable distribution, and register redirect `https://app.signalbox.run/api/oauth/callback`, the exact user scopes in that manifest, and no bot scopes. ElevenLabs uses the existing official catalog app with each person's own API key. Enter it through the secure native connection form; no hosted OAuth app or deployment secret is needed. The key must permit `GET https://api.elevenlabs.io/v1/user` for its health check and any selected tools. Keys can have endpoint restrictions and expiry. The app uses `api.elevenlabs.io`; regional residency hosts are not supported by this catalog version. This source integration does not establish a live call from a local agent.

AWS uses each person's access key ID and secret access key. Temporary credentials also need their session token. Select a supported commercial AWS region in the secure connection form. One-click OAuth is unavailable for this Signalbox connection. The app reads STS caller identity and lists general-purpose S3 bucket names and creation dates in the configured region. STS identity does not require an IAM permission; listing buckets requires `s3:ListAllMyBuckets` on `Resource: "*"`. GovCloud, China and other AWS partitions are unsupported. The catalog source and its helper mocks do not establish native authorization or a live AWS account call.

Zendesk stays available in the catalog without hosted credentials. Each account selects its own Zendesk site during connection. The native connection binds that site to OAuth authorization, callback, saved grant, refresh, health and API requests. Tool input and catalog query parameters cannot choose or change it. The app keeps current-user and ticket shortcuts and serves the operations from Zendesk's official Support API v2 OpenAPI document. It requests the broad `read`, `write` and `impersonate` OAuth scopes. Reads run without approval; every imported mutation and the `createTicket` shortcut require approval. Zendesk still checks each user's role and plan permissions. The catalog and app use Zendesk's primary logo.

Preserve existing public OAuth clients and confidential BYO clients through the native connection form. A pre-existing compatible public client lets a person sign in without creating a client or entering a secret. Advanced BYO remains available, but asking a person to register their own client does not meet site-plus-sign-in onboarding. If no compatible client is available for the selected site, the connection must report that provider limitation.

A customer's own Zendesk OAuth client is only for that customer's own Zendesk account and is never shared across customers; we continue pursuing a separate global hosted client for cross-customer use.

The optional hosted Zendesk client uses `EXECUTOR_OAUTH_ZENDESK_CLIENT_ID` and `EXECUTOR_OAUTH_ZENDESK_CLIENT_SECRET`; neither selects a deployment tenant. An operator distributing a public integration must satisfy Zendesk's applicable registration, approval and request-metadata rules. The internal-company exception remains separate. Configured credentials alone do not prove registration eligibility or unrelated-company consent. The former `EXECUTOR_ZENDESK_SUBDOMAIN` setting is ignored and not forwarded.

For an approved public integration, set the nonsecret Actions variables `ZENDESK_MARKETPLACE_ORGANIZATION_ID` and `ZENDESK_MARKETPLACE_APP_ID` to the IDs Zendesk assigns. The catalog adds them and the product name to API request headers, including health. Both IDs must be present or both absent; header injection is rejected. No placeholder IDs are sent. Token-endpoint header applicability and live registration remain unverified.
