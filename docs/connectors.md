# Hosted connectors

How each connector signs people in, and the OAuth app or key it needs.

The tools service reads `https://app.signalbox.run/catalog/index.json`. A separate read-only Worker serves official catalog entries and contributed app sources. Entries carry no notices: every app lists with its one-sentence description. The contributed Slack user-token method is carried as a pinned package snapshot until its upstream release. The Zendesk source is served by the Catalog Worker independently of optional hosted credentials. New app sources stay with the catalog while community publication awaits an approved publisher scope and checks against the chosen public host. Relative icons resolve to the official publisher. The feed is outside the tools API Worker bundle; the existing 5.45 MB upload budget stays unchanged.

Create the Google connector as a separate OAuth Web application named Signalbox in a separate Cloud project from sign-in. The current connector project uses External audience and Testing status. Only listed test users can connect; their authorizations and refresh tokens expire after seven days. Production publishing, verification and CASA assessment await operator approval. Register `https://app.signalbox.run/api/oauth/callback` and the authorized JavaScript origin `https://app.signalbox.run`. Enable Gmail, Calendar, Drive, Docs, Sheets and Slides APIs. The consent scope union for these six service apps is:

- `openid`, `email`, `profile`
- `https://mail.google.com/`
- `https://www.googleapis.com/auth/gmail.settings.basic`
- `https://www.googleapis.com/auth/calendar`
- `https://www.googleapis.com/auth/drive`
- `https://www.googleapis.com/auth/documents`
- `https://www.googleapis.com/auth/spreadsheets`
- `https://www.googleapis.com/auth/presentations`

A connection requests only its selected app's scopes. The all-in-one Google app requests additional scopes and APIs; see [its scope and API readiness check](google-connector-readiness.md). Full Gmail and Drive access is intentional. The identity-only sign-in client stays independent of connector grants, consent and rotation. Two clients in one project would still share the project's user cap.

Create a separate GitHub OAuth App named Signalbox with homepage `https://app.signalbox.run` and callback `https://app.signalbox.run/api/oauth/callback`. The official REST app requests `repo`, `read:org`, `workflow`, `gist`, `notifications`, `read:user` and `user:email`. The host's optional `github-oauth` client matches this app; its older GitHub App client remains separate. No app review is required. Organization approval and SAML sign-in can still limit repository access.

Google and GitHub connector credentials are optional and use the four `EXECUTOR_OAUTH_*` secrets in [GitHub Actions secrets](self-hosting.md#github-actions-secrets). GitHub Actions supplies them and Alchemy writes their runtime copies. No person enters a client secret to connect their account. Missing or incomplete pairs are omitted, with one deployment warning per unavailable connector. Sign-in, pools and computer setup deploy independently.

GitLab uses its existing official catalog app unchanged. Register apps named after `brand.oauthAppName` with callback `https://app.signalbox.run/api/oauth/callback` and enable authorization-code and refresh-token access. GitLab.com needs `api` and `read_user`; this coarse scope includes writes. Self-managed GitLab needs a separate client and is not covered by the hosted connection.

Miro uses a [carried board-only package](../src/catalog/miro.json) with exactly `boards:read` and `boards:write`. Miro makes these scopes available on all plans; board permissions and team installation policies still apply. A person chooses a team during consent. Personal OAuth is the first connection method, with a custom OAuth client or access token under Advanced. The pinned API document yields 98 board, content and board-membership tools. Organization and team administration, exports, audit, legal holds, SCIM, session resets and app management are excluded. Queries run without approval and mutations always ask. Revoke access by removing the app in Miro's settings. Source and compiler checks do not establish native OAuth or live-provider acceptance.

To verify the complete Miro tool list, save the API document at the `specCommit` recorded in [its provenance](../src/catalog/miro.provenance.json), then run `bun scripts/connectors-tests/miro-tools.mjs <saved-spec.json>` after preparing and building the pinned framework. The check verifies both SHA-256 digests, compares the app's OAuth declaration with the host definition, and compiles every retained operation through the public framework API. It makes no provider requests.

Supply `EXECUTOR_OAUTH_GITLAB_CLIENT_ID`, `EXECUTOR_OAUTH_GITLAB_CLIENT_SECRET`, `EXECUTOR_OAUTH_MIRO_CLIENT_ID` and `EXECUTOR_OAUTH_MIRO_CLIENT_SECRET` through GitHub Actions. These pairs use the same optional-client behavior as Google and GitHub. The tools API receives only the hosted-client metadata and secret bindings; no connector package or API schema is added to its bundle.

Create an Atlassian OAuth 2.0 (3LO) app in the developer console named after `brand.oauthAppName` (Signalbox), with callback `https://app.signalbox.run/api/oauth/callback`. Enable sharing so other people can authorize it. Add `read:jira-work` for Jira and `read:confluence-content.all` and `search:confluence` for Confluence. The app also requests `offline_access` for rotating refresh tokens. Authorization sends `audience=api.atlassian.com` and `prompt=consent`, and token exchanges use JSON. Atlassian's unreviewed-app warning is accepted for v1. Each person connects their own account; their site's permissions and app access policies still apply. Add the client ID and secret to the two `EXECUTOR_OAUTH_ATLASSIAN_*` [GitHub Actions secrets](self-hosting.md#github-actions-secrets). Both may be absent during deployment.

The combined Atlassian app uses private package name `atlassian`. Its public source baseline, fork revision, file hashes and MIT license are under `src/catalog/atlassian/`. A manifest-only patch changes the captured public `apps` pin to the exact Basalt host version. All five read operations explicitly use `never()` approval. Community publication awaits an approved publisher scope and checks against the chosen public host; [upstream source issue #2370](https://github.com/UsefulSoftwareCo/executor/issues/2370) stays open until publication. Its hosted-client metadata remains a separate Basalt-only tools-service overlay. The provider-specific [PR #2367](https://github.com/UsefulSoftwareCo/executor/pull/2367) is closed unmerged, with the generic operator-configuration proposal tracked in [issue #2382](https://github.com/UsefulSoftwareCo/executor/issues/2382).

For the local Atlassian proof, prepare the E2E runtime as below, set `ATLASSIAN_EXPECTED_SOURCE_SHA256` to `snapshotSha256` in the app's provenance file, and run `npm run check:atlassian`. It verifies both source captures and the manifest-only patch, checks the served pin against the real host release API, and serves the carried app through the Catalog Worker handler. It changes only provider endpoints and host placement to a loopback fixture. The real hosted runtime handles OAuth storage, personal account links, organization-pinned tokens and MCP. Installed Claude Code and Codex use isolated homes, the production config installer and a local model fixture. The isolated Codex process explicitly approves only Signalbox's `call` tool for these read requests. Private diagnostics remain under `.generated/atlassian-proof`. This proves local integration and account isolation; production consent, an actual shared pool and live site access remain separate acceptance checks.

Slack uses the official Web API app with an additional personal user-token OAuth method. Its authorization request sends `user_scope` only and reads `authed_user.access_token`. The method is first in the connect flow and the token method is labelled "Paste a token". The carried package drops the original bot install, which needs a person's own Slack app and a workspace install; our hosted Slack app has no bot user. The separate `slack-rest` hosted client sends credentials only to `slack.com`. The older unlisted Slack MCP client stays separate.

Create a Slack app named Signalbox from [its registration manifest](../src/catalog/slack.manifest.json), enable distribution, and register redirect `https://app.signalbox.run/api/oauth/callback`, the exact user scopes in that manifest, and no bot scopes. Put its credentials in the optional Actions secrets `EXECUTOR_OAUTH_SLACK_REST_CLIENT_ID` and `EXECUTOR_OAUTH_SLACK_REST_CLIENT_SECRET`. Missing both does not block deployment. Workspace policy can require administrator approval. Unlisted apps have history and replies limited to one request per minute and 15 items per request.

ElevenLabs uses the existing official catalog app with each person's own API key. Enter it through the secure native connection form; no hosted OAuth app or deployment secret is needed. The key must permit `GET https://api.elevenlabs.io/v1/user` for its health check and any selected tools. Keys can have endpoint restrictions and expiry. The app uses `api.elevenlabs.io`; regional residency hosts are not supported by this catalog version. This source integration does not establish a live call from a local agent.

AWS uses each person's access key ID and secret access key. Temporary credentials also need their session token. Select a supported commercial AWS region in the secure connection form. One-click OAuth is unavailable for this Signalbox connection. The app reads STS caller identity and lists general-purpose S3 bucket names and creation dates in the configured region. STS identity does not require an IAM permission; listing buckets requires `s3:ListAllMyBuckets` on `Resource: "*"`. GovCloud, China and other AWS partitions are unsupported. The catalog source and its helper mocks do not establish native authorization or a live AWS account call.

Zendesk stays available in the catalog without hosted credentials. Each account selects its own Zendesk site during connection. The native connection binds that site to OAuth authorization, callback, saved grant, refresh, health and API requests. Tool input and catalog query parameters cannot choose or change it. Read tools follow the caller's Zendesk permissions; ticket creation always requires approval.

Preserve existing public OAuth clients and confidential BYO clients through the native connection form. A pre-existing compatible public client lets a person sign in without creating a client or entering a secret. Advanced BYO remains available, but asking a person to register their own client does not meet site-plus-sign-in onboarding. If no compatible client is available for the selected site, the connection must report that provider limitation.

A customer's own Zendesk OAuth client is only for that customer's own Zendesk account and is never shared across customers; we continue pursuing a separate global hosted client for cross-customer use.

The optional hosted Zendesk client uses `EXECUTOR_OAUTH_ZENDESK_CLIENT_ID` and `EXECUTOR_OAUTH_ZENDESK_CLIENT_SECRET`; neither selects a deployment tenant. An operator distributing a public integration must satisfy Zendesk's applicable registration, approval and request-metadata rules. The internal-company exception remains separate. Configured credentials alone do not prove registration eligibility or unrelated-company consent. The former `EXECUTOR_ZENDESK_SUBDOMAIN` setting is ignored and not forwarded.

For an approved public integration, set the nonsecret Actions variables `ZENDESK_MARKETPLACE_ORGANIZATION_ID` and `ZENDESK_MARKETPLACE_APP_ID` to the IDs Zendesk assigns. The catalog adds them and the product name to API request headers, including health. Both IDs must be present or both absent; header injection is rejected. No placeholder IDs are sent. Token-endpoint header applicability and live registration remain unverified.

Run `node scripts/check-connectors.ts --preflight` to verify that the prepared runtime matches `upstream.json`, every carried patch, and the generated pool source. For the local connector proof, prepare upstream's E2E runtime with `bun run e2e:prepare` from `.upstream`, then run `node scripts/check-connectors.ts` from this repository. The pinned E2E collector requires Bun 1.4.2 on PATH. Chromium and an installed Claude Code CLI are required. The runner acquires heavy slots for its install and native CLI processes; start the runner normally so its local servers do not hold a slot.

The proof uses the published Google emulator and a synthetic app with Gmail's scopes. OAuth, token storage, per-person organization-pinned PATs, and MCP authorization use the real pinned runtime. Two users share the hosted app while their account links stay private. Claude loads the production installer configuration, searches the real MCP server, and calls the synthetic Gmail tool; only its model endpoint is simulated. Private diagnostics stay under `.generated/connectors-proof`.

The same runner deploys the Zendesk source served by the Catalog Worker and connects six synthetic accounts across two sites: a stored public client, confidential BYO client and host-managed client at each site. It checks native consent callbacks, refresh rotation, account health, MCP reads, exact-host credential placement, peer-user and peer-client refusal, and ticket-creation approval. An installed Claude client also calls the Zendesk tool with a simulated model endpoint. Provider endpoints and publisher metadata are synthetic; this proves neither live Zendesk consent nor approval of a public integration.

This does not prove the unchanged official Gmail app against Google's production endpoints, or two people sharing a Basalt pool. Those remain live acceptance checks after deployment and provider clients exist. Shipping source does not close that acceptance.

The separate GitLab/Miro runner takes saved official package documents named `gitlab.json` and `miro.json`. Download those from `https://catalog.executor.sh/apps/gitlab.json` and `https://catalog.executor.sh/apps/miro.json` into `.generated/connector-snapshots`, then run `bun scripts/connectors-tests/providers.mjs . .generated/connector-snapshots .generated/connectors-proof "$(git rev-parse HEAD)" "$(git merge-base HEAD origin/main)"` after the same E2E preparation. The runner requires full candidate and base commit hashes, a clean matching checkout and an exact pin-and-patch runtime. Each evidence record includes those pins, patch digests, the original inputs and every actual deployment payload with per-file hashes. The runner first deploys the official source and checks automatic client selection. Its API-call variants substitute local origins and a minimal OpenAPI document, use separate personal accounts in one organization, and assert caller data and peer-account denial through native MCP. A transport success is insufficient; inner execution errors and provider request paths are recorded. This runner does not exercise browser consent, OAuth refresh or live providers. The callback refresh regression is covered separately in the upstream native E2E suite.

Zoho CRM reuses the official `@executor.sh/zoho` app unchanged. Create a Server-based application named after `brand.oauthAppName` with callback `https://app.signalbox.run/api/oauth/callback`. Enable the app's required data centers in its Multi-DC settings and select **Use the same OAuth credentials for all data centers**. Supply the common client ID and secret through `EXECUTOR_OAUTH_ZOHO_CLIENT_ID` and `EXECUTOR_OAUTH_ZOHO_CLIENT_SECRET`. Missing or partial pairs use the same optional-client behavior as Google and GitHub. A person chooses their CRM data center when connecting.

The hosted clients cover US, EU, India, Australia, Japan, Canada, Saudi Arabia and China. The official CRM scope union is `ZohoCRM.modules.ALL`, `ZohoCRM.settings.ALL`, `ZohoCRM.users.ALL`, `ZohoCRM.org.ALL`, `ZohoCRM.bulk.ALL`, `ZohoCRM.coql.READ`, `ZohoCRM.notifications.READ`, `ZohoCRM.notifications.CREATE`, `ZohoCRM.notifications.UPDATE`, `ZohoCRM.notifications.DELETE`, `ZohoCRM.features.READ`, `ZohoCRM.send_mail.all.CREATE`, `ZohoCRM.Files.CREATE` and `ZohoCRM.Files.READ`. Scope names are case-sensitive. This is broad CRM access; edition limits, API credits and administrator permissions still apply. Zoho Mail, People and other products are outside this connector. Live consent and a local-agent API call remain acceptance checks after deployment.

The [carried Slack source](../src/catalog/slack.json) is reproduced from its frozen published package plus [the public app patch](../src/catalog/slack.patch) and a separate [Basalt framework pin](../src/catalog/slack.basalt.patch). Every imported query explicitly runs without approval; every mutation asks first, including side effects Slack describes as GET. The public patch retains its published framework dependency; the Basalt copy pins the prepared host's exact release. [Issue 2368](https://github.com/UsefulSoftwareCo/executor/issues/2368) offers the provider change to the catalog owners. Community publication is on hold until the owner selects a publisher scope and the chosen host supports and verifies the strict nested-grant option.

For Slack, run `node scripts/check-slack.ts --preflight`, then `node scripts/check-slack.ts` after preparing the pinned self-host test runtime. The fixture uses the carried app's actual auth, health check, OpenAPI tools and approvals against a local Slack mock. It checks the first user OAuth method, nested user grant, reads and posts, and private account isolation between two people in the same Slack workspace. The actual setup client writes an isolated test configuration with synthetic credentials and a local MCP endpoint. The full run requires installed Claude to read and post through `signalbox` using a simulated model. Live Slack acceptance remains separate.
