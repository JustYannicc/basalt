## Release updates

The release workflow checks the tools service's v2 releases and the Home and node releases separately. Each candidate has one stable update branch and pull request. Repeated checks reuse that PR and refresh it against current `main`. The pins stay immutable; the pool image downloads and verifies released binaries without modifying them.

The patch registry binds each stable identity and upstream mapping to the SHA-256 of its exact content. Numbered filenames are locators; renumbering preserves the mapping, and reusing a number for different content cannot inherit it. Patch numbers are assigned from the next free number on actual main when rebasing for merge. There are no reservations. An upstream PR is a retirement target only when its contribution covers the whole carried patch. Basalt-only, mixed and unpublished carries use `kind: "overlay"` with a null PR, even if an earlier proposal or a generic subset has an upstream PR. Historical proposals remain documented above. Both kinds can name an `upstream_issue`; an issue reference or closure never authorizes automatic retirement. The versioned native Workflow encryption carry remains upstream in [executor#2369](https://github.com/UsefulSoftwareCo/executor/pull/2369). Keep `EXECUTOR_ENCRYPTED_WORKFLOW_STARTS=true`, the existing state key and the native identity format when adopting it upstream. Member-pool provisioning remains an overlay; [executor#2362](https://github.com/UsefulSoftwareCo/executor/issues/2362) tracks a generic default-app hook. The updater removes a pure upstream carry only when its PR has merged and its merge commit is included in the candidate source. Catalog app snapshots require separate publication and manual retirement. A patch that fails to apply leaves the update PR red. It does not bypass preparation or deploy anything.

An update must pass Check and Release preview on its exact head. The preview uses a temporary per-PR stage with its own database, separate app and pool branches, EU storage, container and signing keys. It enables native email/password sign-in for the dedicated smoke identity only on preview stages. Production keeps password sign-in disabled. The acceptance runner signs in, opens the native pool app, imports dedicated test subscriptions, and runs Claude Code and Codex with separate computer credentials through the public installer. Each client must complete a real model request and authenticated built-in tool search. Public computer observations must confirm both operations. Undo and paired credential revocation must pass too.

The preview job destroys the stage after success or failure and checks that its resources are absent. The close workflow retries cleanup if a run is interrupted. A merge receipt exists only after both live smoke and remote teardown pass. Cleanup manifests are encrypted before upload; raw credentials, client transcripts and preview URLs are never uploaded. Keep `PREVIEW_STATE_KEY` until all previews created with it are removed.

Release merge attempts share one workflow concurrency group. The merge gate requires a successful Check receipt for the exact tested merge commit and its head and current-main parents. It rechecks preview teardown, allowed update files and outstanding review findings, then requests a squash merge with the expected PR head SHA. A stale release branch is updated against main and waits for fresh checks.

The final main read and GitHub's squash merge are not atomic. V1 accepts the remaining window in which another owner advances main between them. Automatic production deployment waits for main's own Check to pass on the exact merged commit, then checks out and deploys that same SHA. A failed main Check prevents deployment. The release concurrency group applies only to release merges.

The gate recomputes database and workflow classification. An observed base change, missing smoke credentials, skipped client, broken patch or failed cleanup blocks the merge. Database and workflow-identity changes receive `manual-release` and the applicable risk labels and never auto-merge. `release-update` continues to identify them for preview cleanup. `RELEASE_UPDATE_TOKEN` must be able to create update PRs and merge them, so their changes trigger Actions. Use a fine-grained token with Contents, Pull requests and Issues read/write, Actions read, repository Secrets read/write for the protected credential export workflow, and permission to merge under this repository's branch rules.

### Dedicated preview credentials

`PREVIEW_SMOKE_EMAIL`, `PREVIEW_SMOKE_PASSWORD` and `PREVIEW_STATE_KEY` are generated directly into Actions secrets. The identity uses the reserved `example.invalid` domain. Deploy credentials remain the Actions secrets listed in [GitHub Actions secrets](self-hosting.md#github-actions-secrets).

The protected `Preview credential export` workflow imports the two pool subscription files directly into Actions secrets. Connect throwaway Claude and Codex subscriptions from your native own-pool app's **Accounts** tab (**Connect new account** under **Subscription**). That dialog is part of the dashboard, so it works while app UI hosting is disabled. Then dispatch the workflow on `main` with that pool's actual organization, app and owner IDs and each exact account ID. Confirm these are dedicated test accounts first. The `production-release` job runs without an approval step. The workflow signs a pool-scoped request; the Worker verifies ownership, exact account membership and provider type before exporting the unmodified login file. Home management stays private. No login file is logged or uploaded as an artifact.

Obtain the IDs through your signed-in session: `/api/auth/get-session` gives `user.id`, `/api/auth/organization/list` gives the organization, and `/api/organizations/<organizationId>/inventory` gives the selected pool's `apps[].id`. Query `/api/organizations/<organizationId>/apps/<poolId>/data/query` with `{"name":"view","input":{}}`, require `ok:true` and `value.isOwner:true`, and select the Claude and Codex account IDs from `value.accounts[]`. Those subscription IDs differ from inventory account IDs.

The workflow writes `PREVIEW_CLAUDE_AUTH_JSON` and `PREVIEW_CODEX_SUBSCRIPTION_AUTH_JSON`. Supply `PREVIEW_CODEX_CLI_AUTH_JSON` separately from the genuine native `auth.json` produced by `codex login` in a fresh, dedicated `CODEX_HOME`. It is separate from the pool subscription export.

Set Actions variables `PREVIEW_CLAUDE_MODEL` and `PREVIEW_CODEX_MODEL` to exact model IDs available through those subscriptions. The runner does not substitute models or credentials. It uses private files for login imports and never reads a developer's existing client configuration.

### Database changes and rollback

The deployment compares the candidate with the last successful production deployment. Normal releases auto-merge and deploy. A database change, workflow step identity change, or uncertain classification requires a manual release. Its PR explains the evidence and carries `manual-release` with `database-change` or `workflow-identity-change`.

Dispatch the manual release workflow for that PR. A change already merged to `main` needs no dispatch: when Deploy classifies its head as needing the manual path, it starts `Manual release of main` for that commit itself, even when `main` has moved on. That release ships the newest passing `main` commit that contains it, and stops without deploying when production already contains that commit. Deploy also skips a commit production already has, and hands off rather than deploying a commit that a newer passing `main` commit contains. A manual release's backup job must finish before the deployment job starts in the `production-release` Actions environment. That environment allows only `main` and has no approval step. The backup covers both logical databases on the production cluster and records the previous and candidate pins. Nothing quiesces writes first: a database-changing release migrates production while it keeps serving, and the completed backup is the recovery point. When checkpoint identities change, the release job lists Cloudflare Workflow instances and fails before deploying if any is not complete, terminated or errored. Drain or terminate them, then dispatch again. The listing is an observation, not a lock, so stopping new work comes first.

When Cloudflare rejects a Worker upload because its startup exceeded the CPU time limit (`ScriptStartupError`), the deploy step runs the whole deploy once more before failing, unless part of the first attempt is still running. When a release fails, the next release on `main` that contains its commit rolls forward over it: it deploys from the last success and re-applies the failed release's migrations and data steps, keeping whatever they already wrote. That relies on migrations and data steps being forward-only. Only a single failure rolls forward; if the release rolling forward fails too, releases stay blocked until someone acts. A release job killed before it could record its failure, by a timeout, cancel or lost runner, counts as failed 15 minutes after the Actions run attempt its deployment record names has completed, so database work the killed job started can finish first; until then, or without that record, it blocks releases as before. A release that would drop a gate the failed one needed, such as a revert that no longer changes the database, doesn't roll forward. A failed `Manual release` of a pull request records its head commit, so after a squash merge only a re-release of that PR's branch rolls forward over it, not the next `main` release. Undoing a failed release's database writes is a deliberate rollback that restores the backup the failed release took, which is what the rolled-forward release records as its rollback point. Before restoring, set the `PRODUCTION_RELEASE_HOLD` repository variable so no release runs; then restore, dispatch `Manual production rollback`, and clear the hold. See [deploy safety](../scripts/deploy-safety/README.md#rolling-forward-over-a-failed-release).

For a normal release, rollback automatically redeploys the previous pins and their patch set. For a database-changing release, stop new work. Dispatch `Manual production rollback` on `main` with `release_sha` set to the exact latest database-changing release, including a release whose deployment succeeded before a problem was found. First read the release's recorded backup name from its GitHub production deployment payload (`backupName`, e.g. `gh api 'repos/<owner>/<repo>/deployments?environment=production'`) and restore that exact backup. Then dispatch with `restored_backup` set to that name. The plan fails unless it matches the recorded backup. The rollback job then runs without an approval step, and for a Workflow identity change it stops while any Workflow instance is unfinished. The trusted runner validates the deployment and recorded baseline, rebuilds the exact previous commit in a separate checkout, deploys it, and requires its public smoke check before recording success. Database restore remains manual in v1; a code revert alone does not reverse migrations. Never destroy production as a rollback operation. Losing state metadata remains recoverable through adoption; losing its encryption key remains the documented recovery limitation.

The simulated release and broken-patch checks verify update mechanics without cloud credentials. Live preview, automatic release merge, database restore and provider teardown acceptance remain pending until the required accounts and dedicated subscription secrets are configured.

## Verification and remaining work

`npm run check` exercises routing, configuration, the pool control API and the pool screen's helpers without credentials. `npm run check:providers` compares the provider table with the pinned Home source. `npm run check:build` renders the built sign-in pages and the patched emails under the brand and under a swapped name, and fails if either shows the tools service's name. `npm run prepare:upstream` prepares the pinned source; `npm run check:upstream` exercises the patched namespace adapter, empty-state recovery plan and encrypted Workflow replay; `npm run typecheck` checks Basalt scripts, router and the pool Worker; `npm run typecheck:upstream` runs the pinned upstream's own `bun run typecheck` over the patched checkout, so a carried patch fails Check on any type or Effect diagnostic error upstream's CI would reject; `npm run build` builds the upstream framework and every Worker the stack deploys, router included. Run installs, builds, checks and typechecks through the machine's shared heavy-work limiter when developing on a shared host.

`npm run check:startup` gates every built Worker against Cloudflare's [startup and size limits](https://developers.cloudflare.com/workers/platform/limits/#worker-startup-time). Cloudflare rejects an upload whose global scope needs more than 1 second of CPU to start (`Script startup exceeded CPU time limit`, code 10021), and any Worker over 64 MiB uncompressed. After `npm run build` and `bun install --cwd scripts/startup-profiler --frozen-lockfile`, the check starts each Worker's uploaded modules in workerd five times, the way `wrangler check startup` does, and fails when the median startup CPU exceeds 400 ms or a Worker exceeds 32 MiB. It counts only the modules the main module imports and fails if the global scope throws. Each start runs a small fixed witness right before and after the import; a start counts only when V8's sampler caught both, so a start with almost no work of its own still measures. Starts the sampler missed are retried with backoff; if too many miss, the Worker fails as inconclusive, under its own error title. Local CPU differs from Cloudflare's: other projects report Cloudflare measuring about 3–4 times a developer machine's profile, and GitHub's runners measure about three times an Apple-silicon machine (Api: about 200 ms against 65 ms). The 400 ms budget leaves twice that Api baseline for runner-to-runner variance while staying under half the limit. `node scripts/worker-startup.ts --profiles <directory>` writes each start's CPU profile for Chrome DevTools or VS Code. The Check workflow prints the table in its summary.

The deploy smoke test checks the homepage redirect, the branded sign-in page, logo and MCP metadata, the protected MCP endpoint and unauthenticated model-key rejection. It does not prove interactive Google sign-in. The broad upstream source typecheck has existing dependency/type failures; it is not a passing gate here. Release acceptance also requires signing in with Google into an empty workspace and reading back the actual Postgres region, R2 jurisdiction and Durable Object jurisdiction from the deployed resources. Source settings and placement hints alone are insufficient.

The deployment model can be derived from [alchemy.run.ts](../alchemy.run.ts).

Artifacts app-source repositories use a separate namespace that the stack creates with immutable EU jurisdiction before exposing the public router. Deploys reject an existing namespace outside the EU. App source and compiled builds are separate stores; both require their own EU configuration.

Cloudflare Workflows have no configured EU jurisdiction. The carried patch encrypts step values, callback failure payloads and terminal results before journal persistence, and hashes checkpoint names. Workflow metadata still has no enforced EU placement. Inputs and final outputs are encrypted in Postgres separately. The legacy import workflow is disabled for this deployment.

The Google own-client picker behavior is proposed in [upstream #2459](https://github.com/UsefulSoftwareCo/executor/pull/2459). Its current carry also adapts existing product-specific labels and a shared E2E helper, so it remains a manual-retirement overlay. Inclusion of the generic upstream change alone does not retire the complete carry.

The `executor-shared-catalog-oauth-clients` carry contains the reviewed Notion, Todoist and Trello definitions and their real-server setup scenario. Its [upstream PR #2458](https://github.com/UsefulSoftwareCo/executor/pull/2458) mapping retires only that carry after the merged change is included and the required proof passes. `basalt-shared-catalog-client-labels` is a separate product-label overlay and requires manual retirement review; merging the generic upstream change cannot retire it. Deployment credential forwarding stays in Basalt.
