# Feedback and telemetry

What the feedback form, error reporting, request timings and product analytics send, and where.

`SENTRY_DSN`, `SENTRY_OTLP_ENDPOINT`, `POSTHOG_PROJECT_KEY` and `POSTHOG_HOST` are optional GitHub Actions settings. The DSN enables the feedback form and error reporting. Copy the exact direct OTLP trace endpoint from that project's Client Keys settings into `SENTRY_OTLP_ENDPOINT`; the DSN alone does not select a trace endpoint. Both Sentry settings must use the same EU ingestion host. `POSTHOG_PROJECT_KEY` selects the product analytics project. Set `POSTHOG_HOST` to that project's exact `https://us.i.posthog.com` or `https://eu.i.posthog.com` ingestion origin. Omission preserves the EU default. Product analytics currently uses an existing US project; Sentry remains in the EU. Missing settings disable the corresponding feature and produce a deployment warning.

The dashboard sidebar's Feedback form (carry 0047) sends what the person writes, their authenticated account ID and a fixed page label to Sentry. Unless the person unticks them, it also attaches a screenshot of the page, captured in the browser when the form opens, and recent page logs: up to 50 console errors and failed requests from this page load, as method, path, status and timing, within 16 KB. The browser keeps those logs in memory only and redacts them as it records them: no request or response bodies, headers, cookies, query strings or fragments, and tokens, keys, long hex or base64 strings and email addresses are replaced. The feedback host checks their shape and caps and redacts them again before sending them as a `logs.json` attachment. Agent feedback uses the same destination. Feedback text, screenshots and logs never enter product analytics. The deployment sets the form's endpoint only when a valid feedback destination is configured, so the sidebar shows no Feedback entry otherwise.

Product events use opaque account IDs and a closed property allowlist. Catalog misses carry a known service identifier only when the local catalog yields one unambiguous match; the raw query never leaves the tools service. Product analytics never receives names, email addresses, credentials, tool arguments, results or model content. Browser autocapture and person profiles are disabled. All vendor requests originate in Workers and omit client headers.

Each request the pool forwards to its runtime produces one timing event. It says how long the request spent:

- in the Worker before the pool's Durable Object was called (`workerMs`);
- only when the Worker sent the request to the object again, after a call the platform said to retry, one the object refused while handing over to new code, or one its runtime refused before the container send: the failed or refused call and the wait before the next one (`replayMs`). If the failed call reached the object, that attempt may have its own event;
- waiting for that object's handler to start, including the network hop to it (`queueMs`);
- in admission: the organization check, identity and membership (`admissionMs`);
- in dispatch: runtime readiness, protection and routing, including retries (`dispatchMs`);
- between handing the request to the runtime and its response headers (`firstByteMs`), or until it failed without answering (`unansweredMs`);
- in the response body (`streamMs`), only while model history observes that body.

`totalMs` is their sum, and `durationMs` is evlog's own measure of the time inside the forwarding step (near zero on an event the Worker reports). The dispatch stages Home reports arrive as `home…Ms` fields, with `homeFaults` naming a stage that did not finish. The event also has a closed `outcome`, the response status, the response size when the body was observed, and the guard and cause of a refusal.

To group a burst it carries the pool's request ID, a trace ID, the number of model streams already open and `poolRef`, a short hash of the pool's ID.

It names the runtime that gave the caller its answer. `runtime` is `root` for the pool's own runtime, `cell` for an extra runtime of its fleet, or `candidate` for a release probe; `slot` is `legacy` for the pool object's own container, otherwise the runtime slot's ID; `imageInput` and `boot` are that runtime's image input and boot ID. A call no runtime was sent, refused or held until it timed out, has `unplaced` in all four; the Worker's own event has `unknown` when the pool object ran the call and then failed or ended, since it may have sent the call on. A call that moved, because the runtime it was placed on failed before its send, names the runtime that answered it; a call a runtime had already been sent is never moved, so a failure there and the refusal built from it name that runtime. The root's `imageInput` is `unknown` only on a pool Worker without its image setting. How the call ended is `status`, the response status the caller got, and `outcome`. Calls the extra runtimes served in the last hour, by image: filter the pool Worker's events over that hour on `runtime` = `cell` and an `outcome` other than `unsent`, `refused` and `runtime_refused` (an attempt a cell refused before its container send is re-sent and counted by the event of its final send), and count them grouped by `imageInput`. The request ID is the `X-Request-Id` the caller received on a model call; a runtime's refusal answers under its own ID, recorded as `responseRequestId`. A valid `traceparent` from the caller is continued, so its trace ID is the caller's. Nothing else from a request or a response enters the event: no path beyond a fixed route label, no other header, no body, no model name, no person and no key.

The event is written to Workers Logs. When both Sentry settings are present and the trace is sampled, it is also sent to Sentry as one trace: the event's fields on the request's span and one child span per step that took a millisecond or more.

A call that fails without an answer from the Durable Object is reported by the Worker, with one of these outcomes. After a replay, the outcome and the wait describe the last call.

- `controller_unavailable`: the object never ran it, for example because it is overloaded. The wait is `queueMs`.
- `controller_failed`: the object's own code threw. The wait is `unansweredMs`, because the Worker cannot tell queueing from work there.
- `controller_reset`: the call failed in a way the platform says to retry, for example because the object's instance ended, and no second call was answered. The wait is `unansweredMs` for the same reason. If the Worker answered with retry advice or an unknown outcome, the event carries that answer's status and `X-Request-Id`.
- `client_closed`: the caller disconnected while its request waited for the object. The wait is `unansweredMs`. Such a caller may also leave no event.

These requests produce no event: one refused for a missing or invalid key, one the Durable Object answers without forwarding, and the Worker's own prewarm. Nor does a stream the object had started answering when its instance ended: the Worker saw an answer, and the object that would have reported it is gone. Its `POOL_CONTROLLER_INTERRUPTED` log line remains, and the rest of the stream, when the new instance resumes it, produces no event either. A call the object refuses while it hands over to new code produces no event either, once the Worker stops sending it again. The Worker resends only a model call it holds and a safe read; every refused call still leaves one `POOL_CODE_HANDOVER_WAITED` line with its cause, its request ID, its endpoint and how many times it was sent again, `0` for one it could not resend. A call its runtime refused before the container send ran nowhere: its event has the outcome `unsent`, and the Worker sends it again under the same request ID, so the event of the send that is answered carries the final outcome. When the new instance answers a later send instead, that instance reports the call, and `replayMs` covers the wait from its first call. A caller who leaves while the Worker waits to send again is reported as `client_closed` instead, without that line.

The pool availability probe runs every minute, and every run writes one `POOL_PROBE_RAN` line: `target` (`pool`, `invalid` or `unset`), `verdict` (`ok`, `failing`, or `skipped` with no target), `failed` (`none`, `availability`, `reliability` or `both`) and `sentry` (`yes` when Sentry accepted every part of the run, else `no`). It never names the target. A minute whose only line is an `ok` one ran and was all fine, and a minute with no line did not run. A `failing` run whose `failed` is `reliability` still sends an `ok` check-in, so it opens no Sentry incident. A minute that is not all fine also writes one `POOL_PROBE_VERDICT` line before any alert is sent. `availability` is the failing guards and reasons, or null. `reliability` lists each state (`below_target`, `failing_now`, `collection_unavailable`, `usage_rollup_stuck`, `capture_hours_stuck`) with the windows it was decided on (`current`, `hour`, `day`), and the counts of those windows: real and proof requests, failures, failures by status, failures no account was named for, and unknown outcomes by cause. A stuck history state names the pool's 16-hex history ID instead of a window, and one whose state could not be read that minute is marked `unread`. The line keeps every failure; an alert carries the first eight. When Sentry does not accept a minute's check-ins or events, the run fails with `Pool availability alert delivery failed:` followed by each refused part (`check_in:<status it carried>:<answer>` or `event:<error code>:<answer>`, the answer being Sentry's HTTP status, `no_answer` or `unconfigured`), so a refused check-in on a healthy minute reads as exactly that.

A request from another app through the pool's app-model route has no `workerMs` or `queueMs`, and its admission starts when forwarding does. A refusal the routing layer builds after a runtime failed to answer counts as `unansweredMs`. Inside a fleet, the wait for a runtime's own Durable Object is part of `firstByteMs`. So is a held call's re-send: a call a hold made wait that its runtime refused before the container send is sent again inside the same request, and its refused sends and the pauses between them count from the first send, as `firstByteMs` when one is answered and as `unansweredMs` when the last is refused too. That request then ends as `unsent` with no later event, because it is past the Worker's replay window.

The activation funnel uses `sign_up`, `pool_created`, `account_connected`, `setup_started` and `first_model_request`, in that order. `setup_completed` follows successful model and MCP tool observations and can be measured after first use. Local tests prove event shapes, authenticated web and agent feedback delivery to a capture server, redaction and Worker compatibility. Actual vendor ingestion, EU project configuration and a real activation funnel require live acceptance after deployment.

API Worker size checks enable the optional destinations with synthetic settings. The upstream cold-start budget remains 5,450,000 bytes of uncompressed JavaScript. Vendor SDKs are not added by the destination patches; the router uses small HTTP transports. Direct Sentry error and trace exporters send fixed codes, fixed route labels and closed attributes, never exception text. Cloudflare platform trace export is disabled in this mode because it can include raw URLs or IP addresses.
