# Basalt

Basalt is Signalbox's identity, inference and connectors component. It deploys independently so the Signalbox OS can consume its gateways later.

For existing installations, use the [cutover runbook](docs/cutover.md) and its owner-only login-file importer. Live acceptance and the coordinator's explicit shutdown gate precede removal of any old resource.

This repository deploys the cloud build of [Executor v2](https://github.com/UsefulSoftwareCo/executor) using its Alchemy stack. Upstream owns sign-in, workspaces, connections and MCP. Basalt supplies deployment configuration and a small public router. The model gateway runs the released pool backend. Every person gets their own pool, an app in the tools service that connects subscriptions to that backend.

## Public endpoints

| Path               | Handler                                                             |
| ------------------ | ------------------------------------------------------------------- |
| `/` and app routes | Tools service, including its own Google, GitHub and passkey sign-in |
| Brand files        | The logo, favicon and pool fonts, from [public/](public)            |
| `/mcp`             | Tools gateway, with upstream authentication                         |
| `/v1` and `/v1/*`  | Model gateway, with the pool backend's client-key authentication    |
| `/pool/v1/*`       | Pool control API for pool apps, with a signed per-pool token        |
| `/setup`           | Computer setup page, using the tools service's browser session     |
| `/setup/v1/*`      | Computer list, setup links, per-computer pool switch and paired credential revocation |
| `/share`           | Share page for a pool's owner, using the tools service's browser session |
| `/share/v1/*`      | The pool's people, invitations by email or link, removal, each person's usage and their cap |
| `/setup/claim/*`   | Single-use credential handoff, expiring after five minutes         |
| `/v8/management/*` and `/v0/management/*` | Not public; 404. Home management uses the internal controller path |

The router preserves incoming URLs, headers and bodies, and streams responses through a private service binding. OAuth callbacks and discovery documents reach the same tools service. Only the router owns the public custom domain. Cloudflare provisions it from the existing zone through the deploy token.

The tools service's Worker also serves its own marketing site, docs and legal pages on every host. The router never forwards them: a signed-out `/` goes to sign-in, and the Docs, Privacy and Terms paths redirect to the brand's own pages once `brand.links` names them, and answer 404 until then. The tools service shows those links only when they are set.

[brand.ts](brand.ts) is the one brand config: the name, logo, host and zone, MCP entry name, OAuth app name, email domain and the brand's own docs and legal links. A rename changes it and the files in [public/](public); every place the tools service shows a name follows. [upstream.json](upstream.json) is the only tools-service commit pin. The generated upstream checkout and dependencies are ignored by Git.

## Deployment

A successful Check run for a push to `main` triggers [Deploy](.github/workflows/deploy.yml) on that exact commit. It validates required secrets, checks the router, fetches the pinned public source, applies carried patches, installs its locked dependencies, builds upstream's framework, then deploys through Alchemy. Database migrations finish before replacement Workers serve traffic. Concurrent production deploys are serialized.

Pull requests run secretless checks and builds through [Check](.github/workflows/ci.yml). A patch that no longer applies or a failed build stops the deployment. The stack keeps Alchemy's Cloudflare state backend, so a new Actions runner sees the existing resources. Production Postgres and R2 resources are retained.

Required services are Cloudflare Workers, R2, Hyperdrive, native Email Sending, Artifacts and Containers, PlanetScale Postgres, Google OAuth, and GitHub OAuth. Cloudflare Email Sending delivers sign-in codes and invitations from no-reply on the configured sending subdomain, under the brand's name. The tools service's own welcome note is not sent under another brand. Passkeys carry the brand's name.

Autumn billing, Axiom telemetry and Context.dev company suggestions are optional. When unconfigured, Basalt carries an upstream patch that allows product use without billing, exports no Axiom telemetry and skips company suggestions. It never substitutes hosted emulators. Sentry and PostHog configuration belongs to the analytics integration work.

## Model gateway

[containers/pool/releases.json](containers/pool/releases.json) pins Home and its node to released artifacts and SHA-256 digests. The image runs both unmodified binaries. Home stores credentials, keys, usage and routing state in its own logical Postgres database. The node handles provider requests. `/v1` responses stream through the router, the pool Worker and one Durable Object without buffering model output.

New conversations use round-robin account selection. Session affinity is enabled with a one-hour TTL, and Home fails over when an account becomes unavailable or reaches quota. These defaults are applied at every container boot without replacing stored accounts or keys.

The stack enforces `jurisdiction: "eu"` and `regions: ["EEUR", "WEUR"]` on the container application. The model gateway creates its one control-plane DO through an EU-jurisdiction namespace. These constrain the container and DO independently. They do not constrain the edge router or pool Worker's execution location. PlanetScale's region remains `eu-central` on the single existing cluster.

A two-hour container inactivity timeout plus five-minute DO alarms and a five-minute Worker cron keep the pool warm while the DO sleeps. A host failure or deployment can still restart it. `X-Signalbox-Pool-Boot` on model responses identifies the supervisor boot so the idle acceptance check can detect a restart. A changed image, database credential or management key restarts the container and reloads its runtime secrets.

Cloudflare's `durable_object` scheduling policy enables disk snapshots but rejects container placement constraints. This deployment uses the `default` policy to enforce EU placement. Faster scheduling and snapshot restore remain unavailable with that constraint. See [placement](https://developers.cloudflare.com/containers/concepts/placement/) and [scheduling policies](https://developers.cloudflare.com/containers/configuration/scheduling-policy/).

## Pools

Each person has their own pool from sign-in, empty at first. Once an organization's owner has a verified email, provisioning installs a private pool app for them from [apps/pool](apps/pool), named after them. Members of someone else's organization get no pool there. Sharing a pool uses the tools service's own app sharing. A deleted pool isn't recreated, and a pool its owner has redeployed isn't upgraded. When Basalt's pool source changes, untouched pools are redeployed by delayed member jobs.

The bundled pool app source doesn't ride in the tools service's API Worker code, which is close to its upload budget. The bundler writes it as a static asset named by its SHA-256 (`/_basalt/pool-app-<hash>.json` in the site build), and the API Worker keeps only that hash. Provisioning loads the asset through the Worker's own asset binding and refuses it unless the hash matches. Pools already on the current bundle never fetch it.

The pool app never holds the pool backend's management key, because anyone who can edit an app's code could read it out. Provisioning signs a pool token with `POOL_APP_SIGNING_KEY`, naming the pool, its owner and its organization. It stores the token as the owner's personal account and links it as the app's account. The app sends it to `/pool/v1/*` along with the caller's id from `ctx.user.id`. The pool Worker verifies the token and scopes every call to that pool's channel group in Home. It refuses changes, such as starting a sign-in, pasting a callback, uploading a login file or removing an account, unless the caller owns the pool. Home management calls stay inside the control-plane DO, on the container's port 8327. The owner can also read `GET /pool/v1/usage` for an exact client session (`session`, the wire `X-Session-ID`) or client key (`key`, Home's key id). It returns one `{id, account, status, at}` row per request, limited to the pool's own accounts.

**v1 limit:** an organization's owners and admins can manage every app in it, so they could edit a pool's code to act as its owner, or copy its token out. That's acceptable for v1: organizations are only the sharing boundary and v1 has no admin roles. A person's pool is created only in the organization they own, and sharing adds people as members, so the only owner or admin who can edit a pool is its owner. A host-signed caller assertion would remove the limit ([executor#2359](https://github.com/UsefulSoftwareCo/executor/issues/2359)). Each pool's record and token name the signing key's version, so rotating `POOL_APP_SIGNING_KEY` (see Rotation and rollback) re-signs and re-links every pool's token and then revokes the old ones.

The owner connects subscriptions the way any account is connected: on the pool app's **Accounts** tab, **Connect new account** under **Subscription**. The pool declares that provider with one sign-in method per provider Home can sign in, plus **Login file**, and runs the steps itself through the tools service's app-acquired account method (carried patch `0025-interactive-accounts`, [executor#2414](https://github.com/UsefulSoftwareCo/executor/issues/2414)). The account the tools service saves holds only the pool's account id; Home keeps the credential, and nobody can update it with new credentials: connect another one and remove the old one. Unlinking or deleting that account on the Accounts tab removes the subscription from the pool and Home first. If that fails, the account stays and the owner can try again. Only someone who could delete the account removes it. A member who linked it for themselves only drops their own link. Deleting the pool app or its organization tries to remove each subscription too, but never waits for or depends on it. A subscription left behind that way can't serve requests, because deleting a pool revokes its keys. It stays in Home until someone removes it there. Pruning such leftovers automatically is a follow-up: the pool app can't do it, because it's gone by then. Home has no endpoint that lists providers, so [src/pool/providers.json](src/pool/providers.json) mirrors the provider switch in Home's source at the pinned release, and the bundler writes it into the app. `npm run check:providers` fails when the table drifts from that source. The table only holds ids and display names. The sign-in flow comes from Home's own sign-in link at runtime: a `redirect_uri` on a local address means the dialog asks for the address the browser lands on, and anything else is a device sign-in that Home finishes by itself. **Login file** pastes a file Home exported. Pools take subscriptions only. Subscriptions connected before this have no account on the tab; the pool's page still removes those.

Released Home v1.1.6 doesn't say which credential a sign-in saved ([CLIProxyAPIHome#168](https://github.com/router-for-me/CLIProxyAPIHome/pull/168) adds that). The control-plane DO serializes sign-ins for every pool. It holds one lock per provider while an exchange can produce a credential, and it files the one new credential by diffing the credential list. A second sign-in for the same provider waits or gets a retryable `busy`. A device sign-in that stops being polled for 60 seconds is cancelled. If the diff isn't exactly one credential, nothing is added. Switch to the credential id once a Home release includes it.

The pool's screen follows the prototype's Accounts view: each account's usage windows, with a bar for what's left, a mark for how much of the window's time is left, and when it resets, plus capacity per provider. Its fonts are the dashboard's own Geist faces. The pool app bundler copies them from the pinned source into the router's static assets, under `/brand/fonts/`, and the page links them across origins. The app compiler drops font files from npm packages, and binary files in the bundled source would ride in the API Worker. The screen opens in the app page’s **App** tab, on an isolated app origin; see below.

Container startup, management endpoints and release validation are documented in [containers/pool](containers/pool/README.md). Local routing and lifecycle tests do not establish live model service: release acceptance also needs test subscriptions, a streamed request, account-affinity and spread checks, and an hour of idle time with the same boot identity.

### Usage and caps

The pool's Usage section follows the prototype's views: tokens and API-equivalent cost as separate views over the last 30 days, per model and per UTC day. The owner sees the whole pool and, per provider, whether to add or remove an account. Anyone else sees only their own requests on that pool, their own cap and when it resets, next to the Accounts view's capacity. The pool Worker filters to the caller before adding anything up, so a member's totals never include anyone else's. The pool app reads it with `GET /pool/v1/usage/summary?days=` (its `usage` tool), using the same pool token and caller. A call without a caller is refused.

The pool app only knows people by id, so the owner's per-person numbers and caps live on the Share page, which already has names from the tools service. Each person's row opens their own chart and models. `GET /share/v1/usage` and `PUT /share/v1/members/:id/cap` check the owner's browser session, then call the pool Worker's signed `usage` and `cap` actions; the signed intent's owner must be the signed-in person. Tools-service user ids stay on the server.

Usage comes from Home's stored request records. Home stamps a record with the time its request started, so a long request lands late, and Home can't sort records by when they arrived. On its five-minute alarm, and on a read when the alarm fell behind, the pool Worker reads in three tiers, each with its own saved place: new records since the last read, every 15 minutes the last two and a half hours again for requests that landed late, and always at least two pages of a slow sweep through the whole 30 days. It reads at most five pages a sync and skips records it already counted, so a request that lands late still counts once. It files each record under the pool whose channel group holds its account, or, for an account removed since, the pool named in its backend user, and under the person in that name. It keeps 31 days of per-day totals in Durable Object storage. Names hold digests, never tools-service ids. Tokens use Home's canonical breakdown when Home declares it complete and fall back to its total otherwise.

Cost is Home's own charge for each request, priced from models.dev's API prices, which Home imports. On the alarm, the pool Worker asks Home to import prices for the models it can serve, once a day or within half an hour of a new model showing up, since a charge is priced when the request happens. A model with a price rule someone set by hand is left out of the import entirely, so no imported long-context band can outrank it. A request Home charged at its `default:zero` fallback, because no rule matched, counts as unpriced and adds nothing to cost; the pool logs models it couldn't price.

"Accounts needed" samples each pool's account limits every five minutes for seven days. Only fresh readings count: Home keeps an account's last windows when a quota check fails, so a reading older than half an hour, or one that didn't change since the last sample, adds nothing. It says add an account when every account of a provider was at a usage limit at once; an account Home marked unavailable for another reason, such as a failed sign-in refresh, doesn't count as at a limit. It says remove one when none hit a limit and every limit window, the short ones included, always had an account's worth to spare. It waits for a day of readings before saying anything.

A cap is optional and off by default, the only setting. The owner sets one per member, in dollars of API-equivalent cost per calendar week, Monday 00:00 UTC. It's Home's own weekly spend limit (`limit_7d_credits`, calendar mode), which applies to every key the backend user owns. That's why each person gets one backend user per pool: a cap on someone in your pool must not follow them into their own pool. Switching a computer's pool moves its key to the other pool's user and channel group in one write. The request that crosses a cap finishes; Home refuses the next one with 429, and the pool Worker replaces that body with "You've reached the weekly cap this pool's owner set for you. It resets Monday 00:00 UTC. Ask them to raise it, or switch this computer to another pool." in the protocol's own error shape. It reads at most 8 KiB of an error's JSON and never touches a successful or streamed response.

### Live pool acceptance

The manual **Pool acceptance** Actions workflow runs `scripts/pool-acceptance.ts`. Before full mode, provision a dedicated `acceptance-<run>` pool with two usable test subscriptions and a computer key scoped to that pool. Store that key as `POOL_ACCEPTANCE_KEY`, enter the pool id and an exact model id from the key's `/v1/models` catalog, and confirm the key is for test use. Finish each subscription sign-in before starting the next. Key issuance belongs to computer setup; this workflow does not provision accounts or keys.

Full mode mints a pool token with the existing Actions `POOL_APP_SIGNING_KEY`, using owner and organization `acceptance`. Before waiting, it reads `/pool/v1/pool` and requires exactly two distinct account ids. It reads the owner-only `/pool/v1/usage` route with original wire session ids and checks every record against those accounts, record counts, stable accounts on repeated conversations and spread across both subscriptions. Test model requests carry only `X-Session-ID` for session correlation; the Worker owns canonicalization. The runner never reads raw management endpoints or needs `POOL_MANAGEMENT_KEY`.

The one-hour idle interval sends no requests from this runner and requires the deployment to be otherwise quiet. It then checks the same boot identity and a valid streamed reply. The subsequent restart observation needs an external controlled deploy or crash while the runner is armed. It reports observed recovery bounds and verifies a changed boot plus a valid stream, rather than treating the observation start as the restart time. `restart-observation` mode skips the idle and affinity checks and needs only the dedicated model key. No restart endpoint is added.

Run credential-free runner checks with `node --test scripts/pool-acceptance/*.test.ts`. Those fixtures exercise the public contracts and error paths; they do not prove live service, global idleness, real CLI setup or cross-node revocation.

Preview automation uses the same entry point, `POOL_ACCEPTANCE_MODE=preview node scripts/pool-acceptance.ts`. The trusted parent workflow supplies `PREVIEW_SMOKE_PULL_REQUEST`, its matching `ALCHEMY_STAGE` of `test-pr-N`, and `TEST_STAGE_DOMAIN` from the owned hosting zone. `POOL_ACCEPTANCE_ORIGIN` must exactly match the router origin derived from that PR and domain. The runner checks this before opening auth files. If supplied, `POOL_ACCEPTANCE_PREVIEW_MANIFEST_FILE` must name the private seeded manifest with the same PR, stage, origin and native app context. The workflow must validate the candidate and manifest before supplying these values.

The runner also requires a seeded verified test user in `PREVIEW_SMOKE_EMAIL` and `PREVIEW_SMOKE_PASSWORD`, and that user's native-installed pool context in `PREVIEW_SMOKE_ORGANIZATION_ID` and `PREVIEW_SMOKE_POOL_APP_ID`. Password sign-in must be enabled only for the isolated test stage. The pool must initially contain no subscriptions. The parent workflow provisions and destroys the isolated hosting and database resources.

Materialize dedicated subscription exports into private regular JSON files with mode `0600` and pass their paths as `PREVIEW_CLAUDE_AUTH_FILE` and `PREVIEW_CODEX_SUBSCRIPTION_AUTH_FILE`. These are the unmodified login files downloaded from each dedicated subscription's Home Credentials screen. The management download endpoint is `/v8/management/credentials/download?id=<id>` on the authorized management UI, which stays private. `PREVIEW_CODEX_CLI_AUTH_FILE` separately points to a genuine dedicated native Codex ChatGPT `auth.json`. Set `PREVIEW_CLAUDE_MODEL` and `PREVIEW_CODEX_MODEL` to exact catalog IDs. The parent workflow owns secret materialization and deletion.

Preview mode signs in through native email/password auth, imports those subscriptions through the installed pool app, claims one public setup link per CLI, and downloads the stage's built `/setup/client.mjs` into a private temporary file. It runs that file with `--payload-file` in an isolated home, then uses installed Claude Code and Codex to search the built-in MCP tool with `{"query":"pool","limit":1}` and return a unique marker. It requires successful native output and fresh model/tool timestamps on the exact newly claimed computer. The same downloaded installer performs `--undo`. Cleanup revokes each computer, verifies its revoked record, requires the old model and tools credentials to fail authentication, removes imported subscriptions, signs out and removes local temporary directories. Returned model and tools URLs must belong to the explicit stage origin.

`POOL_ACCEPTANCE_RESULT_PATH` selects a new `0600` JSON report, whose frozen shape is [preview-result.schema.json](scripts/pool-acceptance/preview-result.schema.json). It contains only version, mode, sign-in/pool/cleanup booleans and the two named CLI check records. Failed or unattempted native runs retain `null` exit and timeout fields. A publishing workflow must independently require version `1`, mode `preview`, both exact clients, every boolean `true`, `exit: 0`, and `timeout: false`. A successful process exit alone is insufficient. The report omits credentials, identifiers, model IDs, origins and raw native output. Hosting teardown needs separate verification by the parent workflow. Live preview acceptance still requires the dedicated secrets and an actual deployed test stage.

## Sharing

A pool's owner shares it from the pool's Share button, which opens `/share` on the public host with the same kind of signed intent. Only the owner can open it. It uses the tools service's own sharing: an organization invitation by email, whose link also works for someone without an account and expires after 7 days, and the app's access setting. The first invitation shares a private pool with everyone in its organization. Membership also permits access to other resources shared with everyone, including the built-in app; it is not strict pool-only authority. A pool the owner shared with groups in the dashboard keeps that.

Someone who joins by invitation and owns no organization yet gets one of their own from the tools service's member job, named after them or their email. Setup pins their tools token to their own organization, where their default personal tools and connections live. Membership does not give them the owner's personal account links. The built-in app needs the caller's own link; without one it returns `AccountRequired` and asks for a connection. App-level account sharing is a separate, explicit permission. Which pool belongs to whom is recorded in organization metadata that only provisioning writes: the tools service strips it from organizations people create and refuses metadata changes, and pool deletions require the app to belong to that organization. Sharing only ever adds people as `member`. The tools service refuses invitations, added members and role changes for any other role, and the dashboard offers no other role (the v1 limit above depends on it). Remove takes the person out of the organization.

Whenever someone can lose or gain a pool, the tools service tells the pool Worker the pool's new audience before its own change commits: sharing, groups, removing a member or leaving, deleting the pool, removing the organization and deleting an account. It signs the change (`sba1`, 30-second expiry) with `POOL_APP_SIGNING_KEY` and posts it to `/pool/v1/access`; the contract is [src/pool/access-contract.ts](src/pool/access-contract.ts). The pool Worker deletes the computer keys of everyone who lost the pool, marks those computers removed and refuses setup intents issued to them shortly before the change, so a tool call authorized just before removal can't mint a key after it. The tools service commits only after every key deletion succeeded, so a failure leaves the person in place, with a retryable error. A request already running can finish; the next one fails. Their tools token stays: tools are theirs. The pool Worker also tries to create the pool backend user of everyone who gained a pool (one per person per pool, see Usage and caps); if that fails it stays pending without blocking the change, and the first key mint creates the user. Deleting a pool revokes its computers' keys. Deleting an account revokes every key on the pools that person owns and every key of their own, then deletes their pool backend users. Deletions refuse access for a short time rather than for good, so a deletion that rolls back recovers on the person's next setup. Older setup intents and stale membership snapshots can't bring removed access back.

## Computer setup

The pool's Computers section opens setup on the public host. A short-lived signed intent identifies the pool and caller, on the person's own pool or one shared with them. The setup host checks the person's verified browser session, creates a tools token pinned to the organization holding that person's own pool through the tools service's native API-key flow, and asks the pool controller for one user-bound model key. Tools stay the person's own on a shared pool; only the model key points at it. The controller creates the pool's channel group before issuing a key. An empty Home channel list would allow every credential, so setup never sends one.

The copied prompt contains a one-time link, never either credential. The link expires after five minutes. The controller stores encrypted credentials and consumes the link durably before returning its instructions. Reads and scheduled cleanup erase expired ciphertext. Browser list and update responses expose only computer metadata. Revocation deletes the model key first, then the tools token, and stays visibly unfinished until both succeed. Rebinding changes the existing key's channel restriction on the server; no client secret changes.

The installer requires Node.js 18 or newer. It respects `CLAUDE_CONFIG_DIR` and `CODEX_HOME`, backs up each file before writing, and marks its entries using [brand.ts](brand.ts). Claude Code gets the model gateway URL and token, discovery and timeouts. Codex gets a provider with `requires_openai_auth = true` and `X-Api-Key`. Both get the branded MCP server with the tools token. Other providers and servers remain. Undo is a separate paste or installer `--undo`; untouched files return byte for byte, and later unrelated edits survive. Backups and installer state stay in a private directory on that computer.

The setup page lists every computer the person has, in every pool they can use, and each one's pool. Picking another pool is one click: the controller re-points the computer's existing key to that pool's channel group with the same guarded write, so nothing changes on the computer and its next request uses the new pool. The list of pools comes from the pool controller's directory, which the tools service keeps current (see Sharing). Switching happens only on the setup page, under the person's own browser session, never through a pool app's tools: a pool's owner can edit its code and send any caller id (the v1 limit above), so a pool app could otherwise move someone else's computer onto it. For the same reason a pool app asking for someone other than its owner sees only that person's computers on that pool.

Codex needs any ChatGPT sign-in. Account-side features follow that account's plan. The Claude desktop app is not covered. The computer turns green after a successful model request scoped to its key and pool, plus an observed successful tools call. Catalog reads and MCP initialization do not count.

Source and local checks are separate from release acceptance. Live acceptance still needs a deployed stack, connected test subscriptions, actual CLI requests with matching usage records, unchanged-secret pool switching, and denial of the next model and tools requests after revocation. App screens are enabled in source through opaque same-site origins. Live routing and certificate acceptance still need a deployed check.

After resetting lost deployment metadata on a healthy state backend, redeploy from Actions to adopt named infrastructure and regenerate database roles.

Redeploy cannot recover a lost or rotated state key; after bootstrap, back up `AlchemyStateStoreEncryptionKey` as the Actions secret `ALCHEMY_STATE_ENCRYPTION_KEY_BACKUP` and restore the original value in Cloudflare before deploying again.

### Account setup

Create a Cloudflare token for the account owning the configured zone. Account permissions: Workers Scripts Edit, Workers R2 Storage Edit, Hyperdrive Edit, Account Settings Read, Secrets Store Edit, account SSL and Certificates Edit, Workers Observability Edit, Artifacts Edit, Containers Write and permission to publish container registry images. ### App UI hosting

App screens open inside their dashboard page’s **App** tab. Apps with a deployed UI select that tab by default; tool-only apps keep Overview. Explicit tab and tool links keep their destination. **Open in new tab** remains available. The Apps list marks apps with an App screen.

[brand.ts](brand.ts) enables hosting with `scheme: "opaque"`, `embedded: true` and `origin: "https://signalbox.run"`. Deployment sets `EXECUTOR_APP_UI_BASE_URL`, `EXECUTOR_APP_UI_ADDRESS_SCHEME=opaque` and `EXECUTOR_APP_UI_EMBEDDED=true`. The carried patch defaults upstream to `nested` and embedding off. `EXECUTOR_APP_UI_MANAGED_ROUTE=false` leaves routing to Basalt’s router.

The reserved app-host namespace is exactly `a-<lowercase app UUID>.signalbox.run`: remove `app_` from the immutable app ID and prefix `a-`. Product hosts must never use this namespace. App and organization renames keep the same opaque origin. Resolution yields the immutable app and its current organization before authorization; a later public readable-host mapping can use the same resolution boundary. Public hosting and custom domains are outside this change.

These single-label hosts fit the deployment’s existing `*.signalbox.run` certificate. Opaque mode does not provision per-organization domains, require Advanced Certificate Manager or run the domain controller. Nested mode keeps upstream’s managed-domain behavior. The router forwards only exact opaque app hosts to the tools service’s app-page Worker, before path routing, and never serves dashboard assets or pool/setup APIs on them.

Cloudflare [does not support infix wildcards in routes](https://developers.cloudflare.com/workers/configuration/routing/routes/), so `a-*.signalbox.run/*` cannot be a route. The deployment uses a proxied wildcard DNS record and `*.signalbox.run/*`; explicit product-host bypasses preserve existing custom-domain origins. The router returns an empty 404 for other wildcard hosts. `appHosting.bypassHosts` lists custom-domain product hosts without their own more-specific zone route. More-specific existing routes remain untouched. The new DNS record and bypass resources refuse adoption, so they cannot replace existing records or routes. Existing exact DNS records, including email and verification records, keep their normal precedence over wildcard DNS. Live DNS, route precedence and certificate behavior remain deployment acceptance work.

Embedded app responses allow only the dashboard origin in CSP `frame-ancestors`. The dashboard’s `/app-auth` route allows `'self'`; other dashboard documents retain `'none'` and `X-Frame-Options: DENY`. The iframe has the approved sandbox permissions, `clipboard-write`, and no referrer. A host-owned message confirms loading; a missed deadline offers Retry. Router-served HTML, including `/setup`, `/share`, static pages and error pages, also sends `frame-ancestors 'none'` and `X-Frame-Options: DENY`. The tools service’s `/app-auth` response is the only same-origin framing exception.

The app origin, dashboard and redirect callback share the HTTPS `signalbox.run` site while remaining different origins. [WebKit defines a site as a registrable domain and its subdomains](https://webkit.org/tracking-prevention/), so Safari’s third-party cookie block does not make these app frames third-party. This is a documented expectation, not a Safari device test. Existing app sessions remain HttpOnly, Secure, SameSite=Lax `__Host-executor_app` cookies without a Domain attribute. Dashboard authentication uses Better Auth’s supported `advanced.cookiePrefix`, `useSecureCookies` and default attributes so every core and plugin cookie starts with `__Host-executor-hosted.`, has `Path=/` and `Secure`, and has no Domain attribute. This replaces `__Secure-executor-hosted.*`; old names are never read. Existing browser sessions do not survive this name change, so people sign in once again. Session rows and bearer credentials are unchanged. Dashboard routing hints, last-organization memory, time-zone preferences, passkey prompts and anonymous visitor cookies also use host-only names on HTTPS. Cross-subdomain anonymous signup attribution stops; same-origin attribution remains. Same-site does not allow app code to read the dashboard DOM, host-only dashboard cookies or another app’s session. The server also checks the exact request origin and session target. Isolated test stages keep hosting disabled until they have their own app DNS and certificate configuration.

### Rotation and rollback

Keep the encryption key stable. Replacing `EXECUTOR_ENCRYPTION_KEY` without re-encrypting existing credentials makes them unreadable. Rotating `BETTER_AUTH_SECRET` can invalidate sessions.

Rotate the pool signing key in two deploys. First copy `POOL_APP_SIGNING_KEY` into `POOL_APP_SIGNING_KEY_PREVIOUS`, set a new random 32-byte hex `POOL_APP_SIGNING_KEY` and deploy. About 15 minutes after the deploy, member setup re-signs and re-links every pool's token, so the pool Worker has the new key before any pool uses it. The Worker keeps accepting old tokens meanwhile. Wait at least an hour before you delete `POOL_APP_SIGNING_KEY_PREVIOUS` and deploy again; after that, old tokens stop working. A pool whose token still names the old key at that point gets 401 until its next member setup re-signs it.

Rotate MCP signing keys over three deploys. First put a new random signing key in `MCP_SESSION_KEY_PREVIOUS` and deploy. Next swap `MCP_SESSION_KEY_CURRENT` and `MCP_SESSION_KEY_PREVIOUS` and deploy. Finally replace `MCP_SESSION_KEY_PREVIOUS` and deploy again. Both keys are independently generated 32-byte hex strings. Retiring a key causes sessions signed only by it to initialize again.

Roll back by reverting the upstream pin and carried patch changes together and redeploying through Actions. A code rollback does not reverse committed database migrations. Review database changes before updating, take a backup first, and restore it when required by that release. Never destroy the production stack as a rollback step.

Copies someone changed, and updates that would break accounts, are never deployed: they become an offer that the app's Versions tab shows with the number of accounts to reconnect, and its Update button deploys through a manager-only endpoint. Upstream preparation writes the release revision. This Basalt-only overlay stays manual.

- `0028-embedded-app-ui.patch` adds optional embedded app screens and opaque app origins. Upstream proposal: [UsefulSoftwareCo/executor#2419](https://github.com/UsefulSoftwareCo/executor/issues/2419). It changes no stored database schema or workflow identity; retirement requires a reviewed equivalent upstream implementation and browser proof.


Existing runs from the earlier encryption patch must be drained before deploying this revision because their parameters have no format marker. Basalt has not deployed that earlier format. Keep this format marker and native ID scheme when adopting the generic upstream implementation. Basalt explicitly enables `EXECUTOR_ENCRYPTED_WORKFLOW_STARTS` for this fresh installation. Existing upstream installs must first deploy marker-aware dispatchers with that gate disabled, wait for earlier invocations to finish, then enable it in a second deploy. After activation, retain marker-aware code for rollback. Later changes to Workflow checkpoint names require a separate compatibility assessment or drain.

Each carried patch is applied against the one pinned upstream source. Pure upstream carries can retire when their complete equivalents are included by a later pin. Basalt-only and mixed overlays require a reviewed manual change; adopting a generic part never retires their operator-specific content.

## Release updates

The release workflow checks the tools service's v2 releases and the Home and node releases separately. Each candidate has one stable update branch and pull request. Repeated checks reuse that PR and refresh it against current `main`. The pins stay immutable; the pool image downloads and verifies released binaries without modifying them.

The patch registry binds each stable identity and upstream mapping to the SHA-256 of its exact content. Numbered filenames are locators; renumbering preserves the mapping, and reusing a number for different content cannot inherit it. Patch numbers are assigned from the next free number on actual main when rebasing for merge. There are no reservations. An upstream PR is a retirement target only when its contribution covers the whole carried patch. Basalt-only, mixed and unpublished carries use `kind: "overlay"` with a null PR, even if an earlier proposal or a generic subset has an upstream PR. Historical proposals remain documented above. Both kinds can name an `upstream_issue`; an issue reference or closure never authorizes automatic retirement. The versioned native Workflow encryption carry remains upstream in [executor#2369](https://github.com/UsefulSoftwareCo/executor/pull/2369). Keep `EXECUTOR_ENCRYPTED_WORKFLOW_STARTS=true`, the existing state key and the native identity format when adopting it upstream. Member-pool provisioning remains an overlay; [executor#2362](https://github.com/UsefulSoftwareCo/executor/issues/2362) tracks a generic default-app hook. The updater removes a pure upstream carry only when its PR has merged and its merge commit is included in the candidate source. Catalog app snapshots require separate publication and manual retirement. A patch that fails to apply leaves the update PR red. It does not bypass preparation or deploy anything.

An update must pass Check and Release preview on its exact head. The preview uses a temporary per-PR stage with its own database, separate app and pool branches, EU storage, container and signing keys. It enables native email/password sign-in for the dedicated smoke identity only on preview stages. Production keeps password sign-in disabled. The acceptance runner signs in, opens the native pool app, imports dedicated test subscriptions, and runs Claude Code and Codex with separate computer credentials through the public installer. Each client must complete a real model request and authenticated built-in tool search. Public computer observations must confirm both operations. Undo and paired credential revocation must pass too.

The preview job destroys the stage after success or failure and checks that its resources are absent. The close workflow retries cleanup if a run is interrupted. A merge receipt exists only after both live smoke and remote teardown pass. Cleanup manifests are encrypted before upload; raw credentials, client transcripts and preview URLs are never uploaded. Keep `PREVIEW_STATE_KEY` until all previews created with it are removed.

Release merge attempts share one workflow concurrency group. The merge gate requires a successful Check receipt for the exact tested merge commit and its head and current-main parents. It rechecks preview teardown, allowed update files and outstanding review findings, then requests a squash merge with the expected PR head SHA. A stale release branch is updated against main and waits for fresh checks.

The final main read and GitHub's squash merge are not atomic. V1 accepts the remaining window in which another owner advances main between them. Automatic production deployment waits for main's own Check to pass on the exact merged commit, then checks out and deploys that same SHA. A failed main Check prevents deployment. The release concurrency group applies only to release merges.

The gate recomputes database and workflow classification. An observed base change, missing smoke credentials, skipped client, broken patch or failed cleanup blocks the merge. Database and workflow-identity changes receive `manual-release` and the applicable risk labels and never auto-merge. `release-update` continues to identify them for preview cleanup. `RELEASE_UPDATE_TOKEN` must be able to create update PRs and merge them, so their changes trigger Actions. Use a fine-grained token with Contents, Pull requests and Issues read/write, Actions read, repository Secrets read/write for the protected credential export workflow, and permission to merge under this repository's branch rules.

### Database changes and rollback

The deployment compares the candidate with the last successful production deployment. Normal releases auto-merge and deploy. A database change, workflow step identity change, or uncertain classification requires a manual release. Its PR explains the evidence and carries `manual-release` with `database-change` or `workflow-identity-change`.

Dispatch the manual release workflow for that PR. A change already merged to `main` needs no dispatch: when Deploy classifies its head as needing the manual path, it starts `Manual release of main` for that head itself. If `main` has moved on, the newer head's own Deploy run does it instead. Its backup job must finish before the deployment job starts in the `production-release` Actions environment. That environment allows only `main` and has no approval step. The backup covers both logical databases on the production cluster and records the previous and candidate pins. Nothing quiesces writes first: a database-changing release migrates production while it keeps serving, and the completed backup is the recovery point. When checkpoint identities change, the release job lists Cloudflare Workflow instances and fails before deploying if any is not complete, terminated or errored. Drain or terminate them, then dispatch again. The listing is an observation, not a lock, so stopping new work comes first.

For a normal release, rollback automatically redeploys the previous pins and their patch set. For a database-changing release, stop new work. Dispatch `Manual production rollback` on `main` with `release_sha` set to the exact latest database-changing release, including a release whose deployment succeeded before a problem was found. First read the release's recorded backup name from its GitHub production deployment payload (`backupName`, e.g. `gh api 'repos/<owner>/<repo>/deployments?environment=production'`) and restore that exact backup. Then dispatch with `restored_backup` set to that name. The plan fails unless it matches the recorded backup. The rollback job then runs without an approval step, and for a Workflow identity change it stops while any Workflow instance is unfinished. The trusted runner validates the deployment and recorded baseline, rebuilds the exact previous commit in a separate checkout, deploys it, and requires its public smoke check before recording success. Database restore remains manual in v1; a code revert alone does not reverse migrations. Never destroy production as a rollback operation. Losing state metadata remains recoverable through adoption; losing its encryption key remains the documented recovery limitation.

The simulated release and broken-patch checks verify update mechanics without cloud credentials. Live preview, automatic release merge, database restore and provider teardown acceptance remain pending until the required accounts and dedicated subscription secrets are configured. The tracking issue stays open until a real release completes the entire flow.

## Verification and remaining work

`npm run check` exercises routing, configuration, the pool control API and the pool screen's helpers without credentials. `npm run check:providers` compares the provider table with the pinned Home source. `npm run check:build` renders the built sign-in pages and the patched emails under the brand and under a swapped name, and fails if either shows the tools service's name. `npm run prepare:upstream` prepares the pinned source; `npm run check:upstream` exercises the patched namespace adapter, empty-state recovery plan and encrypted Workflow replay; `npm run typecheck` checks Basalt scripts, router and the pool Worker; `npm run build` builds the upstream framework and every Worker the stack deploys, router included. Run installs, builds, checks and typechecks through the machine's shared heavy-work limiter when developing on a shared host.

`npm run check:startup` gates every built Worker against Cloudflare's [startup and size limits](https://developers.cloudflare.com/workers/platform/limits/#worker-startup-time). Cloudflare rejects an upload whose global scope needs more than 1 second of CPU to start (`Script startup exceeded CPU time limit`, code 10021), and any Worker over 64 MiB uncompressed. After `npm run build` and `bun install --cwd scripts/startup-profiler --frozen-lockfile`, the check starts each Worker's uploaded modules in workerd five times, the way `wrangler check startup` does, and fails when the median startup CPU exceeds 400 ms or a Worker exceeds 32 MiB. It counts only the modules the main module imports, and fails if the global scope throws or V8's sampler stalls on every retry. Local CPU differs from Cloudflare's: other projects report Cloudflare measuring about 3–4 times a developer machine's profile, and GitHub's runners measure about three times an Apple-silicon machine (Api: about 200 ms against 65 ms). The 400 ms budget leaves twice that Api baseline for runner-to-runner variance while staying under half the limit. `node scripts/worker-startup.ts --profiles <directory>` writes each start's CPU profile for Chrome DevTools or VS Code. The Check workflow prints the table in its summary.

The deploy smoke test checks the homepage redirect, the branded sign-in page, logo and MCP metadata, the protected MCP endpoint and unauthenticated model-key rejection. It does not prove interactive Google sign-in. The broad upstream source typecheck has existing dependency/type failures; it is not a passing gate here. Release acceptance also requires signing in with Google into an empty workspace and reading back the actual Postgres region, R2 jurisdiction and Durable Object jurisdiction from the deployed resources. Source settings and placement hints alone are insufficient.

The deployment model can be derived from [alchemy.run.ts](alchemy.run.ts). Architecture modeling and its CI checks attach there in separate work.

Artifacts app-source repositories use a separate namespace that the stack creates with immutable EU jurisdiction before exposing the public router. Deploys reject an existing namespace outside the EU. App source and compiled builds are separate stores; both require their own EU configuration.

Cloudflare Workflows have no configured EU jurisdiction. The carried patch encrypts step values, callback failure payloads and terminal results before journal persistence, and hashes checkpoint names. Workflow metadata still has no enforced EU placement. Inputs and final outputs are encrypted in Postgres separately. The legacy import workflow is disabled for this deployment.

## Feedback and telemetry

`SENTRY_DSN`, `SENTRY_OTLP_ENDPOINT`, `POSTHOG_PROJECT_KEY` and `POSTHOG_HOST` are optional GitHub Actions settings. The DSN enables the feedback button and error reporting. Copy the exact direct OTLP trace endpoint from that project's Client Keys settings into `SENTRY_OTLP_ENDPOINT`; the DSN alone does not select a trace endpoint. Both Sentry settings must use the same EU ingestion host. `POSTHOG_PROJECT_KEY` selects the product analytics project. Set `POSTHOG_HOST` to that project's exact `https://us.i.posthog.com` or `https://eu.i.posthog.com` ingestion origin. Omission preserves the EU default. Yannic approved the existing US project temporarily for #1418, overriding #1400's EU choice for product analytics; Sentry remains in the EU. Missing settings disable the corresponding feature and produce a deployment warning.

The feedback button sends only what the person writes, an image they choose, their authenticated account ID, a fixed page label and recent error codes to Sentry. Agent feedback uses the same destination. Feedback text and screenshots never enter product analytics. The UI remains hidden when no valid feedback destination is configured.

Product events use opaque account IDs and a closed property allowlist. Catalog misses carry a known service identifier only when the local catalog yields one unambiguous match; the raw query never leaves the tools service. Product analytics never receives names, email addresses, credentials, tool arguments, results or model content. Browser autocapture and person profiles are disabled. All vendor requests originate in Workers and omit client headers.

The activation funnel uses `sign_up`, `pool_created`, `account_connected`, `setup_started` and `first_model_request`, in that order. `setup_completed` follows successful model and MCP tool observations and can be measured after first use. Local tests prove event shapes, authenticated web and agent feedback delivery to a capture server, redaction and Worker compatibility. Actual vendor ingestion, EU project configuration and a real activation funnel require live acceptance after deployment.

API Worker size checks enable the optional destinations with synthetic settings. The upstream cold-start budget remains 5,450,000 bytes of uncompressed JavaScript. Vendor SDKs are not added by the destination patches; the router uses small HTTP transports. Direct Sentry error and trace exporters strip arbitrary exception text and attributes before sending. Cloudflare platform trace export is disabled in this mode because it can include raw URLs or IP addresses.
