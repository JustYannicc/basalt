# Basalt architecture

This directory holds the hand-written model. It shows Basalt's modules, outside-service calls, current runtime, planned v1 modules, and workflows.

- `spec.c4` defines the model vocabulary and styles.
- `model/` defines Basalt and the relationships between its modules.
- `views/` contains sparse current and planned overviews plus v1 workflows. Computer setup, observation and revocation live together in `views/workflows/computer-setup.c4`.
- `gen/*.gen.c4` is generated from the stack declaration inventory and must not be edited by hand.
- `CONTEXT.md` is the machine-readable vocabulary used by architecture checks.

The router module maps to `src/router.ts` and declares `TOOLS_SERVICE=basalt.toolsGateway`, `POOL_SERVICE=basalt.modelGateway`, and `CATALOG_SERVICE=basalt.catalog`. The tools gateway is one dependency boundary mapped to `.upstream/apps/hosted/cloud`; public identity, connectors, and vault interfaces are shown without expanding the dependency's internals. Its dynamic, per-person destinations use one `outsideServices` boundary reached through the tools gateway. Fixed infrastructure outside services must have separate adapter elements with host and SDK metadata from the stack inventory.

Feedback is a separate module mapped to `src/feedback` and `public/feedback.js`; its host checks the tools service's native cookie session and hands accepted submissions to Telemetry. Router, Model gateway and Setup host also call Telemetry. The opaque tools-service boundary can post analytics and agent feedback through the authenticated router relay. Telemetry sends feedback, errors and traces to the EU diagnostics adapter and account-scoped product events to the configured regional product analytics adapter over HTTP. Product events exclude content, credentials and email and keep `AccountConnected` separate from `app_installed`. Empty tool-search events never include query text; they include a catalog `service_id` only when one unambiguous local match exists. The diagnostics adapter uses a wildcard EU ingest host, supported by the source scanner. The OTLP URL comes from its Client Keys settings and stays on the same EU origin. The code does not derive it from the DSN.

`SENTRY_DSN`, `POSTHOG_PROJECT_KEY`, `POSTHOG_HOST` and `SENTRY_OTLP_ENDPOINT` are optional settings. Deployment omits absent or empty values from Router and Pool Worker environments. It derives the relay token from the signing key, sets `TELEMETRY_RELAY_KEY` on Router and supplies `EXECUTOR_TELEMETRY_RELAY_URL` with `EXECUTOR_TELEMETRY_RELAY_TOKEN` to the tools-service API Worker when the optional relay is configured. Router checks that token.

The resource inventory evaluates the actual root stack with synthetic required settings and the checked-in deployment choices. Network access is denied. Two explicit read fixtures provide a zone and an empty retirement-gate script list; any other request fails. The evaluator registers declarations without running provider lifecycle operations or provisioning commands. Exported stateful classes are inventoried with their owning worker and drawn inside it. The generated binding digest preserves known declaration names and kinds while deferred binding contributions stay unresolved. It does not inspect a live account. The source scanner covers Basalt-owned build, deployment and runtime code in the repository root, `src/`, `packages/`, `containers/`, `scripts/`, and declared execution paths. Workflow action/image references, container build files and their literal host/SDK inputs use the same outside-service rule. Package installs identify their package source, and unknown download destinations or image registries fail. Tests and architecture verification tooling have separate ownership. It excludes the pinned dependency's internals under `.upstream/` and maps that tree as one code boundary. Python source uses AST parsing without importing or executing inspected code. Container source is checked across build and runtime stages. Docker input ownership also contributes to the source fingerprint checked during generation. Build owns the verified release downloader and image inputs; Deployment owns provisioning and public-route smoke checks. Release, container-registry, package, hosting-control and database-control services have explicit caller relationships. Brand configuration is shared data, with callers shown through import relationships. Unsupported context selection and unresolved runtime destinations fail. The dependency's internal host and import inventory is outside the owned-source check.

The runtime bundle-size check uses synthetic telemetry endpoint values so its bundle includes the enabled transport. It does not send requests to the observability adapters. Native stack inventory also supplies synthetic telemetry settings to evaluate optional declarations without contacting those services.

The current router sends `/v1` and its descendants plus the signed `/pool/v1/*` control API through `POOL_SERVICE` to the model gateway. The pool app calls that control API through the public router with a per-pool signed token and the tools caller identity. The controller scopes accounts to the pool's channel group and permits changes only for its owner. Both public entry points reject `/v0/management` and `/v8/management`; port 8327 stays internal to the controller. The router redirects a signed-out homepage visit to `/login`, serves brand assets, and blocks or redirects the tools service's site pages. Dashboard, MCP and OAuth traffic uses the tools service binding. The gateway uses one EU control-plane actor and one warm EU container running the released control-plane and inference binaries under a Python supervisor. Container placement uses the default scheduling policy with EU jurisdiction and east/west EU region constraints. The pool database is separate within the existing EU cluster and uses a direct connection with verified TLS. At deploy time it uses the tools service's cluster and schema-owner role through their registered resources rather than references to deployed state, so a first production deploy plans without prior state; inside a Worker it refers to deployed state.

The disabled app-hosting origin is represented as a planned deployment boundary. The pool app and its Accounts screen are implemented in source. The tools service installs one private instance per verified person per organization, upgrades its bundle and links a signed pool token. Ownership checks are implemented, and sharing uses the tools service's built-in sharing. Computer setup (#1411) is implemented in source through a root `/setup` page and same-origin HTTP host. Model requests through the app remain planned. Opening the pool app through app hosting remains planned while that origin is disabled. Source checks do not establish live setup acceptance.

The build supplies the patched `apps` framework to the tools compiler through `EXECUTOR_APPS_FRAMEWORK` and `EXECUTOR_APPS_VERSION`. Deployment supplies `POOL_APP_SIGNING_KEY` to the router, pool Worker and tools service. The bundler copies the token signer into the upstream tree. It writes the pool app as a static asset named by its SHA-256 (`/_basalt/pool-app-<hash>.json` in the tools service's site build), so the API Worker's code carries only the hash, and provisioning loads the asset through the Worker's own asset binding after checking the hash. It also copies dashboard fonts into `public/brand/fonts/`; the router serves those fonts with CORS from `public/_headers`. The provider catalog check reads pinned Home source from the Provider source adapter.

Computer setup has two source boundaries. The Setup host maps to `src/setup`, including `host.ts` and the root `ui.tsx` entry. The Config installer maps to `src/setup/client.mjs`, `config.mjs` and `files.mjs`. The root React screen reuses `apps/pool` UI components and is served as static assets by the router. It does not require the disabled app-hosting origin. The pool app requests a signed setup intent from `/pool/v1/setup-context` using its pool token and caller identity, then opens `/setup` with that intent. The setup host checks the tools service's native cookie-authenticated session, requires a verified user, and creates or deletes that user's personal PAT through native auth endpoints. It calls `/__setup/v1/*` only through the private `POOL_SERVICE` binding with an action-bound signature and a 30-second expiry. Public requests to the internal setup prefix are rejected.

The existing model gateway owns computer registration and encrypted one-time credentials in the pool controller's storage. It generates a model key and registers it to the user with a nonempty pool channel-group list. Setup links expire after five minutes and are durably consumed before returning either credential. Revocation deletes the model key before the native personal PAT, with retryable state if PAT deletion fails. Undo restores local config separately. The installer backs up files, writes marked model-client config, and preserves later unrelated edits during undo. `/v1` model passthrough stays unchanged. Successful model usage for the exact key and current pool binding, plus a real successful `/mcp` tool call observed through an internal signed action, determine whether the computer turns green. Initialization and tool listing do not count.

Deployment's preview acceptance mode derives its router identity from the trusted workflow's PR number, matching test stage and owned test domain. The supplied origin must match that derivation before the runner opens auth files. A supplied private deployment manifest must also match the seeded native app context. The trusted parent validates candidate provenance and binds that identity to the deployed router; a caller-provided URL alone supplies no authority. Named `stageRouter` adapters send native cookie auth, installed pool queries and mutations, public setup calls, installer download and revoked-credential probes to that validated origin. Each CLI gets its own claimed computer and isolated temporary home. The runner executes the downloaded built installer and uses the same file for undo. Successful native model replies and MCP search calls require fresh server observations on that exact computer. The report exposes only the frozen versioned booleans and CLI exit/timeout results. Parent automation owns isolated hosting provision and teardown; a runner report does not prove those resources were removed. Tests with fake protocol peers establish runner behavior only. Live preview acceptance remains pending.

Build prepares the frozen setup dependencies in `scripts/prepare-upstream.ts`. `scripts/setup-build.ts` bundles the installer asset and root React page with esbuild from the pinned dependency. `src/setup/package.json` pins `smol-toml` 1.8.0 with its own `bun.lock`; the installer parses and writes JSON and TOML rather than editing text patterns. The source scanner includes `.mjs` runtime files under the same import, host and unknown-call rules as TypeScript. A supplied link does not waive the requirement for a statically traceable router destination. This model adds no concrete outside service for setup; native auth and pool management use the existing tools and pool bindings.

The separate catalog Worker carries the maintained messaging package with its contributed user-only OAuth method. Its feed metadata selects that method first. The hosted client requests user scopes without bot scopes and selects the nested personal token. Only a readiness boolean reaches the catalog; client secrets stay in the tools service. Missing credentials are visible before connecting. Real messaging identity and same-workspace isolation remain live acceptance checks.

Current public identity, connector and vault behavior belongs to the pinned tools dependency. The Basalt-facing identity, connection and vault interfaces remain planned integrations. Workflow descriptions distinguish those targets from the running transport.

Every PR that changes modules, outside services, deployment or flows updates this directory in the same PR. Keep module interfaces and outside services in the authored model; regenerate deployment files instead of editing them.

Install the check tooling with `bun install --cwd scripts/architecture --frozen-lockfile`. Prepare the pinned dependency with `bun run prepare:upstream` before inspecting the stack, then run `bun run --cwd .upstream/apps/hosted/cloud framework:build` to prepare its framework reference. Then run:

```sh
bun run architecture:format
bun run architecture:validate
bun run architecture:model
bun run architecture:typecheck
bun run architecture:inventory
bun run architecture:deployment
bun run architecture:validate
bun run architecture:test
```

CI runs format and validation first, then generated element types and typechecking, then deployment regeneration with a clean-diff check and validation, then the fitness tests. Validation includes layout drift. The deploy workflow also regenerates element types before its existing typecheck.

Pure brand data uses `configuration "true"`; this is valid only for literal constant declarations. Host and SDK metadata use exact evidence keys on external adapters, while visible names stay in the domain language.

Each owned module has `metadata { code '<relative path>' }`. `bindings` maps source service bindings to model element IDs. `resources` lists the stable resource IDs printed by the inventory command, separated by `|`; each resource maps to exactly one logical element. The generator creates a deployment instance for each resource and stores its ID in instance metadata. IDs are `resource-` followed by the lowercase SHA-256 of the full resource type, a NUL separator, and its fully qualified name. Missing, stale and duplicate mappings fail generation. The dependency checkout itself is excluded from the fingerprint; its pin and carried patches are authoritative. Every generation evaluates the current stack and recomputes a source fingerprint over the local stack source graph, container context inputs, public asset bytes, dependency pin and patches. Generation fails if those inputs change while it runs. The CLI prints the source fingerprint in the CI log; it is never committed into the diagram. The committed output contains resource instances and the native declaration/binding digest. Source-only edits leave that output unchanged. Resource, binding-name or binding-kind changes still require regeneration and a clean-diff check. Opaque setting values and live provider state remain outside the native digest. After rebasing, regenerate only if the deployment structure changed; CI still regenerates and checks every PR. The existing PR requirement to update architecture documentation for runtime or stack changes remains in force.

Code naming model elements imports `$ElementId` from the generated module under `scripts/architecture/gen/`. That module is rebuilt in CI and ignored by Git. Renaming an element without updating its code references fails typechecking. The source check requires an explicit relationship for cross-module imports and service bindings, and an external element plus caller relationship for concrete outside hosts and SDKs. Unresolved computed fetch destinations fail instead of being assumed safe.

Dynamic-view steps are checked against model relationships. Real trace comparison and live provider-state comparison are outside this check.

Release automation accepts published tools versions, verifies CI on the exact merge commit against current main, and serializes only its own merge workflow. It refreshes stale release branches and waits for new proofs. Dedicated subscription exports use the existing owner-scoped pool control API and write directly into Actions secrets from a protected trusted-main workflow. Database rollback restores remain manual; the rollback dispatch validates the latest successful or failed database deployment before rebuilding and deploying its previous commit.

Deployment enables `EXECUTOR_ENCRYPTED_WORKFLOW_STARTS` for the fresh tools-service installation. Its dependency patch versions native app Workflow identities and authenticates persisted results. Existing upstream installations need a separate dispatcher cutover before enabling that setting.

The release gate serializes its own squash merges and checks current main plus exact merge-result CI immediately before the expected-head merge request. V1 accepts a main advance between that check and the request. Production deployment waits for a successful main push Check from the CI workflow and uses that run's exact SHA for checkout, reporting and deployment. Failed main CI cannot trigger deployment. Patch identities bind content digests and upstream mappings; numbered paths are locators that owners renumber against actual main at merge.

Product analytics accepts only the exact EU and US ingestion origins. `POSTHOG_HOST` selects the region; omission preserves the EU default. Yannic authorized the connected US project temporarily for #1418, overriding #1400's EU choice for product analytics. Diagnostics still use the EU region.
