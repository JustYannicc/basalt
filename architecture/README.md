# Basalt architecture

Zendesk connections prefer the configured global client. Without it, a host-owned public-client definition derives the identifier from the validated tenant subdomain and uses the existing PKCE, encrypted grant and exact-site placement paths. The public path requests read and write only. An unauthenticated authorization check follows no redirects and submits no consent; a client or callback refusal returns the one-time admin setup step before the browser leaves. Provider outages and rate limits remain separate failures. A tenant admin must register the hosted callback even when a local MCP callback already works. No tenant settings change during connection, and each grant retains its original client for renewal.

This directory holds the hand-written model. It shows Basalt's modules, outside-service calls, current runtime, planned v1 modules, and workflows.

The connector acceptance runner persists its active phase before each step and its latest successful assertion count. CI retains that checkpoint and a bounded child-output tail containing only closed phases, error categories and repository-relative source positions. Raw child output and session files remain private, including after a forced stop.

The tools gateway pins its authentication dependency overlays to Better Auth and core 1.7.5. Social token and signing-key fetches refuse redirects; administrator updates cannot replace a user ID, and banned users cannot acquire a new session through a context-free adapter call. These checks protect the identity that account and pool authority rely on, while the existing private SSO transport remains responsible for its own requests.

The MCP session Worker uses grant-only authentication options and the admin table columns its reads need. Administration endpoints and session-creation hooks stay on the API and self-host sign-in instances. MCP authentication still uses the shared grant and API-key plugins. This keeps the admin route implementation out of every MCP cold start without changing grants, storage or upload budgets. Worker-size failures retain their full diagnostic cause in CI.

Billing policy and SSO identity verification use separate public scenarios and fresh teams. SSO setup enables Enterprise without running the checkout and seat-synchronization proof. Combining those independent proofs spends the sign-in scenario's fixed 60-second deadline before its protocol completes.

Native device approval lives at `/native/device` on the public app origin. The page uses the existing cookie-authenticated device and setup APIs, checks the native audience and scopes, and refreshes account identity and signed pool context before deciding. A decision with an unknown outcome sends the person back to their device without replaying the write. The generic `/device` flow and the `/setup` redirect keep their existing ownership.

The Config installer enables the provider client's WebSocket capability with `supports_websockets = true`, preserving provider sign-in and the pool's `X-Api-Key`. `GET /v1/responses` follows the existing Router, model gateway, pool controller and container relationships. The model gateway authenticates the handshake before selecting the controller. The controller forwards the upgrade over plain HTTP to container port 8317 and returns the `101` response with its socket; it does not parse frames or store sessions. Existing connections can finish after key revocation, while new handshakes fail. Before reporting a new connection complete, the controller enables `websockets: true` for the relevant model provider credential through the gateway's supported management API and verifies the saved flag. Retries require a successful patch acknowledgment because a saved flag alone cannot prove a runtime reload succeeded. Failed enablement retains the account id for retry without reserving an unattempted membership write. A private operator command reaches a named model-gateway entrypoint through an authenticated remote service binding, then calls the controller's migration RPC. Its dry run returns counts plus a selection digest. Applying requires explicit coordinator GO bound to that selection, permits at most 50 sequential writes and stops on an unconfirmed readback within a thirty-second management deadline. Saved-true credentials are included to confirm their runtime reload. A private started receipt prevents a lost response from silently authorizing another apply. There is no product route or scheduled caller. A downstream handshake alone does not prove the upstream transport. CI covers installer output and undo, credential enablement and retry, the pinned node's persistent handshake, and opaque frames through the built proxy with synthetic key and container-port adapters. Live provider inference remains a separate release check. This adds no deployment resource or storage boundary.

The catalog serves a site-aware repository collaboration package. Each account keeps one exact HTTPS instance origin for authorization, token exchange, refresh, health and API calls; reconnects cannot replace it. The public service keeps the hosted client, while self-managed origins use that instance's client or a token. Existing public-service accounts retain their IDs and implicit origin. Private-origin reachability requires an operator-controlled exact-origin exception. Synthetic runtime and UI checks cover these boundaries; live provider acceptance remains separate. The source verifier copies the provider table when rebuilding the generated pool app for that proof.

Retained-data fixtures must remove later SDK objects before recording an older storage version. SDK 4.0.27 adds app connections and call receipts; older-layout fixtures remove those two tables before replaying the real migration, while retaining the accounts, grants and links each scenario verifies.

The tools gateway can resolve new account connections through a host registration that outlives the acquiring app. Reconnect preserves the saved account identity; explicit deletion uses its retained binding and retry receipt. App removal leaves that account intact, while legacy app-owned connections keep their existing lifetime. Additive layouts 4.0.20 and 4.0.21 extend the complete 4.0.19 layout, and host protocol 20 adds acquisition declarations while preserving protocols 1 through 19.

Canonical provider definitions in `src/pool/provider-accounts` supply app requirements and the cloud host's trusted Home registrations. Optional family metadata describes compatible sign-in choices without changing existing provider IDs. Each consumer declares the capabilities it needs; one SDK planner checks those requirements against installed host adapters. Management apps can save a credential without an inference adapter, while a pool's `model-inference` requirement still refuses unsupported methods. Family metadata alone never grants credential use. OAuth verification uses host-reviewed recipes and preserves each binding's client, resource, placement and confirmed grant coverage. The bundler copies the shared declarations into each consumer; `apps/` contains installable apps only. Existing app-account links let the same saved AccountId supply its management app and several pools, with native reconciliation retaining pool authority. New token accounts commit separately before the authorized app-link operation prepares their mirror, keeping backend I/O outside the transaction and preserving the saved account if linking fails. Jev retains its native System One adapter. Retained model provider accounts move through a named production operation only after the canonical provider apps and compatible pool slots exist. Its reviewed SQL plan preserves account IDs, encrypted credentials, generations and access, and moves completed connection provenance out of the legacy app-owned lifecycle. It calls no provider backend. Native activation and production apply still require separate approval.

Signed pool claims establish a transport token's provenance, but do not close the legacy reconnect race. Unmarked secret methods can create a connection without holding the account lock, so private retirement accepts only provisioned plain-secret methods. Its fixed database operation pins the supported storage layout and refuses identity, OAuth and acquisition-backed accounts instead of bypassing their lifecycle. The host account and its journal receipt share one transaction; an encrypted recovery point is durable first. Home credentials, backend keys and channel memberships retain their existing ownership.

Recorded organization-owned pools complete a missing native membership handoff on authenticated reads, default reconciliation and selection. The handoff changes only the membership marker, retaining saved selections, sharing policy and the provisioned control account. A controller with no membership state obtains current host authority and repairs Home membership before serving the read. Before a native link or audience mutation commits, the tools gateway requires a signed dirty acknowledgement from the pool controller. The controller persists a new revision and stops that pool's streams. Its periodic level read uses the tools service binding and the same native SQL locks, so a failed mutation recovers from rolled-back links. Readback repairs only channel-group details; saved credentials and other pools survive. An explicitly enabled host acquisition registration exposes an opaque Home reference only to this private read. Home membership can arrive late, so it never grants native use: each native model request carries the verified pool and revision to the local scheduler veto. The projection expires after 15 seconds and refreshes every five seconds. Upkeep calls share one active pass, and runtime warming preserves an earlier alarm even when it is already due. A slow pass therefore cannot defer membership renewal to the five-minute lifecycle interval. Gateway refusal logs name the failing guard and a closed cause class without raw exception text. Request assertions have a separate two-hour lifetime for WebSockets. Existing app-owned subscription credentials still require their separate reviewed adoption; the handoff never infers a Home binding. Active model HTTP streams and upgraded sockets retain the container health lease. Its remaining milliseconds are anchored at the controller's request start, so transport delay cannot extend protection. One shared watcher refreshes while streams remain active and closes them at the acknowledged deadline if readiness or the watcher stops making progress.

Pool sharing uses native app audiences, groups and organization roles. A native manager can inspect per-person usage and change weekly caps through the host API without gaining app execution or private-account access. Settings shows each person's totals, per-model daily usage and an inline weekly cap editor. Reads refresh only while visible, drafts survive failed saves, and app changes reset their state. The host holds the organization access lock until its signed pool operation returns, so a concurrent demotion cannot authorize a later cap write. Usage responses omit serving-account references. Old sharing bookmarks resolve to Settings, and the old invitation and organization-removal mutations refuse writes. Deployment preserves existing audience and activation markers; existing-pool activation still requires its own dry run and approval.

`poolUsageSeries` aggregates the append-only model-request ledger behind that same management lock and the saved accounts' inspection policy. The trusted acquisition host resolves current Home bindings; only hashed ledger identities cross to the pool service, and no reference reaches a client. Native mapping is enabled because the pinned live Home fixture proves the credential ID equals the usage row's `auth_index`; that fixture runs in CI on every change. Other people's accounts expose counts only, and foreign imports remain unmapped. UTC bucket reads preserve exact range and provider-window bounds, missing token counts and distinct currencies. Home credits, imported USD prices and an unavailable API-equivalent valuation remain separate. A repeatable-read page is bounded by 500 groups, 5,000 bucket rows and 1 MiB, with a composite keyset and a capture/ingestion watermark; late imports require rereading the range. Latest-ever success uses a separate bounded account lookup. Model-history v3 adds only the `(pool, account, timestamp)` index through the existing reviewed schema plan and GO path. Its 500 ms lock wait and five-second statement limit bound write blocking; deployment never applies it or rewrites history. The query-plan tests assert the account-time index family for filtered reads and the existing pool-time family for grouped reads.

The tools gateway retains released app protocols 15 and 16 with their own provider schemas and validation dependencies. An admitted approval retains its original issuer across renewal; new callbacks and resource reads still require unexpired authority.

Tools-only scoped API keys carry their action policy through MCP access, and their `ext_` prefix makes older hosts reject them after rollback instead of granting full access.

Native Accounts rows show account observations with their reading age and refresh-failure state, retaining the last successful readings after a failed refresh. Each product authorizes inspection and refresh separately from account use; denied inspection hides observation details, and credential health remains independent. The observation row renderer and usage-access editor load only after browser hydration, keeping their code out of the dashboard Worker.

The shared workspace-service OAuth client allows the separate administration app's 18 administration scopes while keeping identity-only defaults and ordinary workspace consent requests unchanged. The router module maps to `src/router.ts` and declares `TOOLS_SERVICE=basalt.toolsGateway`, `APP_UI_SERVICE=basalt.toolsGateway`, `POOL_SERVICE=basalt.modelGateway`, and `CATALOG_SERVICE=basalt.catalog`. Its dynamic, per-person destinations use one `outsideServices` boundary reached through the tools gateway. Fixed infrastructure outside services must have separate adapter elements with host and SDK metadata from the stack inventory.

App-origin authorization checks expiry and the parent session on every request. Its Better Auth adapter skips expired-verification cleanup, which the dashboard adapter still performs during sign-in, so a private app query does not scan and delete unrelated expired records.

Dashboard code and data have separate lifetimes. Loaded account and human-in-the-loop components reuse their lazy identity when a page reopens; retained query data still follows the existing refresh and access-denial rules. Workflow-question and app-location bindings retain their family identity for the existing 30-minute period, so garbage collection cannot turn a revisit into a fresh read. Embedded app documents belong to the organization layout, so leaving a console page hides its frame without moving or reloading it. Hidden frames are inert and receive the existing inactive message that pauses their clients. Their visible placement follows the current page's slot. Organization changes and confirmed loss of app access discard retained documents. This is a browser lifetime only; each app request still checks the current session and authority.

The tools gateway shares session, organization, membership and removal checks only within one dashboard batch's streaming request. Each endpoint keeps its resource permission checks, and the next request reads authority again. CI compares the same eight-read page before and after the carry on isolated self-host servers; its PGlite wall times are separate from production Postgres latency. Cloud batches also share the tools gateway's SQL pool and request runtime in a resource scope owned by the HTTP request, outside the reads' child scopes. That scope closes after the reads, and no connection survives into the next request. Installed catalog apps roll forward once per Basalt release. Upstream preparation writes the Basalt revision into the tools service. Its every-minute data step records `basalt-catalog-apps:<revision>` once and queues one member job, 15 minutes later, for each organization holding a copy of this deployment's feed, run as an owner or admin with a verified email. The job reads the feed through the same cached client installs use and only touches copies whose recorded origin is this feed's `apps/<id>.json`. A workspace is clean when it holds the active source, give or take a framework pin, or is still on a commit the job recorded beside a version as holding catalog source. Records carry the digest of that commit's files; records the first sweeps wrote have none, and their commit counts only while it holds the app's first version, the installed catalog copy. When the source has not changed, the job only records the active version, beside the commit read only when it holds that source, else beside the recorded commit while the version is the job's own; after the first catalog deploy, the recorded digest of the applied source decides that, because retained versions keep binary public files by reference. Unsaved workspace edits skip the copy. Otherwise the job first builds the catalog source without saving anything and compares its account requirements with the active version and the app's links. A copy with one version, or whose active version the job recorded, is untouched: it is deployed only when no linked account would stop working, no newly required slot lacks a shared app account or could leave a caller without a personal account and no slot drops to one account while several are linked, and only if the app is still on the version and clean workspace the decision used right before the deploy. The deploy carries that version as the SDK's optional `expectedVersion`, checked under the app's lock before building, before migrations and right before activation, so a person's deploy or activation landing in between fails it with `AppVersionChanged` and nothing is recorded. Only the active version is compared: a person's deploy still building has not activated, so the job's deploy can activate first and leave theirs inactive, as any two overlapping deploys do; checking reservations instead would let an abandoned deploy block every later one. The check before migrations runs in its own transaction, so an activation between it and the migrations is caught only under the final lock, after they ran. It is recorded only when that deploy became active. The job then commits the deployed files to the workspace's main against the commit it read, as upstream's built-in app upgrade does, so a manager's "Deploy latest" does not bring the old source back, and records that commit as the clean one. A workspace that was clean only for its framework pin keeps the pin in that commit. A workspace that moved meanwhile keeps its commit, is left out of the record and counts as touched on the next sweep. Any other commit failure records the commit read, which still holds the replaced catalog source, for the next sweep to heal. Before deciding, the job heals that, and installs the first sweeps deployed without committing: when the app runs the version the job recorded and its workspace is clean on the recorded commit yet holds other source, it commits the active source there against that commit, keeping a framework pin found on a replaced version's source, and records the new commit.
